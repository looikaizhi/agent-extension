# 规格：引导稳定性——单 Agent、工具循环、一次一步

**Status:** ready-for-agent

> 来源：`.scratch/guide-stability/diagnosis.md`（五个症状的代码成因、四个缺失概念、六个同类产品的一手调研）与三轮 grilling 的 16 条决定（2026-09-17 用户逐轮确认）。四条硬决定的理由并进了 `CONTEXT.md` 的词条注记（`Agent`、`Tool`、`View`、`Reading`）——本仓库刻意没有决策记录目录，见 `.scratch/s1-retirement/spec.md`。词汇以 `CONTEXT.md` 为准；本规格里出现的 `View`、`Presentation`、`Reading`、`Actionability`、`Outcome` 的两个字段，都已经有词条。

## Problem Statement

**对用扩展的人：引导常常在说一件已经不成立的事，而且说出口之后收不回来。**

真机 t11 的 52 趟里，被外围终止的 18 趟一趟都没到过目标。用户看到的是五件事：

1. **它在讲我刚离开的那一页。** 我已经点进去了，它给的下一步却建立在上一页的元素上。
2. **框画在了别的页面上。** 话说的是这一页，高亮却落在另一张视图的控件上。
3. **马上就回来的东西被判死。** 页面还在渲染，它已经说「未能定位」；等目标真的出现了，那句话也收不回来。
4. **我照做了，它说我没做成。** 我点了复制按钮、点了在新标签页打开的链接——事情办成了，只是这一页没变——它对模型说的却是「这个控件推不动，换一个入口」。
5. **它卡住了，而且不告诉我。** 结束的时候还有调用在途，屏幕上什么都没有。

**这不是五个 bug，是四个概念缺失加一条机制性错误。**

- 产品没有「这是哪一页」的单一定义，有五个互不兼容的近似物，它们在两个方向上各错一次。
- 产品没有「这一步做成了什么」，`confirmed` 把「用户点了」和「页面变了」焊成一个值，唯一的效果记录只覆盖跨页那一种。
- 产品没有「一次呈现」的身份，状态挂在可变的模块级变量上，重试用尽之后能被重画整套重启，没有终止条件。
- 产品没有统一的超时所有权，至少 9 个独立计时常数在猜同一类事。

**而最根本的一条**：等待失败在别的浏览器 agent 里产生的是**一个模型看得见的错误**，在本产品里产生的是**一条写进历史的断言**——而盖章先到先得、盖过不改，那条假事实此后无法纠正。这是「偶尔测试能过但一直不稳」的机制原因。

## Solution

**把「猜」从产品里拿掉，分成三层，并且收成一个 Agent。**

- **机制层**执行机械规则，不猜：`Actionability` 用 Playwright 的定义（可见、启用、命中测试、连续两帧同 bounding box）；快照过期一律硬失败；每一次点击都记下时刻、元素与发起者。
- **证据层**只记事实：一次点击发生了、点击后的一次观察（带出处）、用户点了别的控件。环境的四个观察源降级为 `Reading`，**只写读数，永不自行推进状态**。
- **判断层**是模型，全部经工具进出：`observe` / `wait_for` / `read_doc` 是 `Tool`，`point` / `ask` / `explain` / `done` 是 `Output`。

**一个 Agent，一次一步。** 问答与引导的分野改成行为判据：一趟里一次 `point` 都没有，就是一次 `Question`。

**两种模式只在「谁发起点击」这一点上不同，下游完全一样**——指路模式靠目标上的 capture 阶段 click 监听同样精确知道点击时刻。本规格**只做指路模式**；`act` 不注册，模型看不见就不可能调用（理由见 `CONTEXT.md` 的 `Tool` 注记）。

## User Stories

**被引导的人**

1. 作为被引导的人，我希望它给的下一步说的是我现在这一页，而不是我刚离开的那一页，这样我不必猜它在讲哪里。
2. 作为被引导的人，我希望高亮框出现在它所描述的那一页上，这样我看到的框和听到的话是同一件事。
3. 作为被引导的人，我希望页面还在渲染时它不要急着下结论，这样一个马上就会出现的按钮不会被说成「未能定位」。
4. 作为被引导的人，我希望目标短暂消失又回来之后那句「未能定位」能被收回，这样我不会被一句已经不成立的话带走。
5. 作为被引导的人，我希望我点了、事情也办成了、只是这一页没变的时候（复制、在新标签页打开），它不要说「这个控件推不动，换一个入口」。
6. 作为被引导的人，我希望在同一页上生效的一步（展开了一个菜单、打开了一个下拉）也算数，而不是因为地址没变就被当成没做成。
7. 作为被引导的人，我希望它卡住的时候明确告诉我卡住了，而不是一直没有下文。
8. 作为被引导的人，我希望一次等待超时只是让它多看一眼，而不是把「失败」写进这一趟的记录。
9. 作为被引导的人，我希望我在站内搜索里换了关键词之后它能跟上，而不是因为按钮长得一样就认为我没动过。
10. 作为被引导的人，我希望在文档站里滚动页面不会让高亮消失。
11. 作为被引导的人，我希望它需要等的时候说清在等什么，这样我知道它还活着。
12. 作为被引导的人，我希望我自己点了别的地方时，它的下一步能把这件事考虑进去。
13. 作为被引导的人，我希望我只是问「这一页是什么」的时候，不会平白开始一趟引导。
14. 作为被引导的人，我希望扩展永远不替我点击，这样页面上写的字不能借它的手去操作我的账号。
15. 作为被引导的人，我希望一趟走得太长的时候它停下来说明白，而不是安静地耗完再消失。

**读这个仓库的人**

16. 作为读这个仓库的人，我希望「这是哪一页」只有一个定义，不必在五个近似物之间挑一个。
17. 作为读这个仓库的人，我希望「这一步被执行了吗」和「这一步做成了什么」是两个字段，这样我不必从一个枚举值里猜出两件事。
18. 作为读这个仓库的人，我希望一次呈现有名字、有拥有者，这样我一眼知道谁有权让它作废。
19. 作为读这个仓库的人，我希望每一个等待都能说出是谁发起的、谁负责超时、超时之后谁告诉用户。
20. 作为读这个仓库的人，我希望产品里不再有「猜页面稳定了没有」的计时常数。
21. 作为读这个仓库的人，我希望模型能调用的函数在一个登记处列全，读一眼就知道它这一步能干什么。
22. 作为读这个仓库的人，我希望「指路模式不注册 `act`」由结构保证，而不是靠提示词里写一句。
23. 作为读这个仓库的人，我希望结构指纹只回答「东西变没变」，永不回答「这是哪一页」，并且这条区分写在词条里。
24. 作为读这个仓库的人，我希望只有一个 `Agent`，不必再对照两份形状不同的定义。
25. 作为读这个仓库的人，我希望修复轮只有一种形状，不必记住两条路径各自的规矩。

**维护这个仓库的人**

26. 作为维护这个仓库的人，我希望归约器仍然是纯函数、能在 node 里秒级跑完，这样它在 service worker 被回收之后仍能靠持久化状态重放。
27. 作为维护这个仓库的人，我希望「扩展不替用户动手」由一个会变红的测试守着，而不是由一句注释守着。
28. 作为维护这个仓库的人，我希望环境触发器不能自行推进状态这一条由测试钉住，这样它不会在某次修改里悄悄退回去。
29. 作为维护这个仓库的人，我希望删掉 latest-wins 队列之后并发重规划不会重新出现，这条同样有测试。
30. 作为维护这个仓库的人，我希望写 Run record 的时候不再把 `effect` 丢掉。
31. 作为维护这个仓库的人，我希望「确认了几步」有一个机械定义，而不是一个会随判定习惯漂移的说法。
32. 作为维护这个仓库的人，我希望配额用完只由整趟步数触发，每步调用用完是收敛而不是终止。
33. 作为维护这个仓库的人，我希望一次等待超时在证据层留下带出处的读数，而不是在历史上盖一个再也改不掉的章。
34. 作为维护这个仓库的人，我希望清扫在途调用的返回值真的被消费，这样超时通知能到达用户。
35. 作为维护这个仓库的人，我希望模型输入的冻结快照在最后一张票重新生成，并在提交信息里写明为什么变。
36. 作为维护这个仓库的人，我希望每张票都能单独验收、票间可以 `/clear`，这样每次实施都从干净上下文开始。
37. 作为维护这个仓库的人，我希望实施过程中不引入任何兼容层或迁移代码，过时的路径直接删掉。

**之后做评估的人**

38. 作为做评估的人，我希望「两批冻结语料在这次之后不可比」写在明处，这样我不会拿不可比的数字去对比。
39. 作为做评估的人，我希望重录语料发生在新架构落地之后，而不是在中间态录一份同样不可比的。
40. 作为做评估的人，我希望真机 harness 不需要改就能跑新架构。
41. 作为做评估的人，我希望指路模式下的到达判据（最终 URL 加最后一步）保持不变，这样这次改动前后的真机数可以直接比。

**之后要开代劳模式的人**

42. 作为之后要开代劳模式的人，我希望机制层到时候不用重写，因为两种模式下游完全一样。
43. 作为之后要开代劳模式的人，我希望开启条件写在 ADR 里，而不是靠谁还记得。
44. 作为之后要开代劳模式的人，我希望到时候的改动面已经被点名：注册一个 `act`、加一个执行动词、重新定义到达判据、改三处词条。

## Implementation Decisions

### 验收尺

- **硬指标**：产品里不存在任何「猜页面是否稳定」的计时常数；「这是哪一页」的实现只有一处；每一个等待都能指出它的拥有者。
- **行为指标**：五个症状各有一条单测，用今天会红、改完会绿的输入钉住。
- **不变量**：`architecture.spec.ts` 的禁用动词断言一条不减，并新增「`act` 未注册」「RPC 无执行动词」两条。

### 页面身份：`View`

- `View` = **完整 URL 去掉 fragment**，不掺任何结构（理由见 `CONTEXT.md` 的 `View` 词条）。
- 旧的 `Place`（origin+pathname）、`pageHash`（再加前 24 个地标）、`pageMoved`（两者之一变）三处实现**删除，不留兼容**。
- 快照的 generation **降级**为只回答「这份快照还新不新鲜」，不再兼任页面身份——这是症状 2 的根因。
- 结构指纹保留，职责改为只回答「这一页上东西变没变」。
- 元素表带 `View` 戳；画一步之前比对，不一致则硬失败，**绝不按描述符重绑**。

### 一步的结果：`action` × `effect`

- `Outcome` 拆成两个正交字段：`action` = `taken` | `skipped` | `unavailable`；`effect` = `moved`（带去向）| `changed_in_place` | `none` | `unknown`。
- `effect` 由 `View` 与结构指纹合成：`moved` 是 `View` 变了；`changed_in_place` 是 `View` 没变而结构或控件变了；`none` 是重新读过这一页、都没变；`unknown` 是每一次都读不到这一页。**等待超时是 `none`**——只有确实读到了页面、每次都没变，超时才会发生。
- **`confirmed` 与 `failed` 两个取值删除。** `failed` 念给模型的是「这个控件推不动」，而真机 t11 里这样记下的 9 步没有一个是死控件：点了、起了作用，只是这一页没变。
- 落点字段删除，**去向并进 `effect: moved`**——模型读到的「之后到了 X」靠它，不能丢。打转兜底改看 `effect`。
- 写 Run record 时**必须带上 `action` 与 `effect`**。
- 「确认了几步」的机械定义：**`action: taken` 且 `effect` 是 `moved` 或 `changed_in_place`**。

### 一次呈现：`Presentation`

- 宿主签发 id。内容脚本的高亮、丢失监听、限次重试全部挂在它下面。
- 宿主换一次呈现，旧 id 的一切计时器与监听立即作废；**内容脚本不得自行续命**。
- 同一次呈现被重画：重试还在跑就沿用剩下的次数，已经用尽就重新找一轮——宿主重画是在回应页面变化，页面变了值得再找。
- 一轮重试用尽要让宿主知道；宿主等到这时才下「找不到」的结论。

### 环境观察源：`Reading`

- 四个观察源（整页导航完成、用户点了我们指的东西、目标消失、页面结构自己变了）**全部降级**，只写一条带出处的读数：何时、看见了什么、谁看见的。
- 它们**永不自行推进状态**。推进与否由模型在下一次 `observe` 读到读数之后决定。
- **latest-wins 队列随之删除**：今天需要它，正是因为四个触发器各自有权直接引发重规划、互相赛跑。
- 「目标消失」不再由宿主抢先写死结论。今天内容脚本一边启动重试一边返回失败、宿主立刻盖章并发「未能定位」，而恢复成功之后**撤不回历史也收不回那句话**。先改成等这一轮重试的结果出来再下结论；有了读数之后，这个结论交给模型。

### 等待的所有权

一条规则：**每个等待由发起它的那一层拥有，超时只产生读数，永不产生写进历史的断言**（理由见 `CONTEXT.md` 的 `Reading` 注记）。

- **模型发起**（`wait_for`，上限封顶）：超时返回「等了 N 秒，没等到 X」，送回模型，**不盖章、不写历史**。
- **宿主发起**（`Presentation` 生命周期、模型调用、文档抓取）：超时进证据层，**并且必须有人告诉用户**。清扫在途调用得出的超时通知，由清扫的那一处当场送给用户（以前两处都算出来就丢掉）。**症状 5 的主因不在这里**：侧栏只执行活动标签页的调用，引导所在的标签页一到后台，派出的调用就没人执行（06a）。
- **机制层**（`Actionability`）：等不到就是「此刻不可操作」这一个事实，不重试、不猜。
- **删除 7 个猜测性计时常数**：三组等待窗口、settling 宽限、限次重试的七档、结构变化的防抖、滚动到目标的上限。只保留机制层的两帧，和宿主的两个传输超时。
- **不用墙钟做产品闸门**：真机 harness 每跳最多等约 45 秒而模型超时 150 秒，墙钟类判据在真机上跑不出来，只能单测验收。

### 工具集与登记处

- 指路阶段注册七个 `Intent`：`observe` / `wait_for` / `read_doc` 是 `Tool`，`point` / `ask` / `explain` / `done` 是 `Output`。
- 沿用上一次 pass 定下的**模块形状与登记处**（一个模块装齐 schema、识别、自己的校验、提示词里那段门槛、后果、trace 摘要）。这部分**保留**，只是内容换掉。
- `wait_for` **独立成工具，不并进 `observe`**：三家同类产品一致这么分，理由是「等」必须由模型说出等什么、等多久；并进 `observe` 就又变回产品替模型猜。
- `read_doc` 就是今天的 `need_docs`，**这次把那半截循环接通**：宿主判定了能抓之后，请求真的交给侧栏，正文真的回到模型。
- `ask` 合并了旧的 `clarify` 与 `need_text`，带一个「要什么」的字段（选一个，或给一段文字），两者后果相同——Thread 停下来等用户。
- `act` **不注册**。工具集随模式变，用结构保证，不用提示词保证。

### 单 Agent

- 两个 `Agent` 合并成一个（理由见 `CONTEXT.md` 的 `Agent` 注记）。独立的问答 agent 连同它的运行循环、它的三个 Output 模块、它那份不含页面的修复轮，**整个删除**。
- **修复轮只剩一种形状**：原请求整个重发，再追加一对 `assistant`(tool_calls) / `tool` 消息说明哪里不对。那对消息靠 `tool_call_id` 配对，是线格式定死的；而要修「ref 不在快照内」这类错，模型手上必须有那张表。代价实测很低。
- **问答与引导的分野改成行为判据**：一趟里一次 `point` 都没有，就是一次 `Question`——不建 Thread、不吃步数预算、不写 Run record。不在入口提前分流。

### 一次一步

- 模型一次只给一步（`point`）。`Route` 保留（粗路标，用于全貌展示与账单前置，允许模型编造），但**永不落成可推进的步骤**。
- 「超时前进」那条路径删除。它今天推进游标却不盖章，那条历史永远停在未知——这是症状 4 的一条根本路径。
- `Fixed plan` 是唯一的多步来源，它的规矩原样保留，**永不调用模型**。

### 两个预算与结束方式

- 旧的「一整趟最多 12 次模型调用」换成两个数：**每步模型调用上限（4）**与**整趟步数上限（12）**。文档抓取的独立计数并进每步预算。
- **每步调用用完不结束这一趟**，而是强制收敛：把当前最好的一步指出来；连一步都指不出来就 `ask`。
- **`quota_exhausted` 保留，但只由整趟步数用完触发。**
- 其余结束方式不变。

### 顺序

每一步做完,产品都照常可用。

1. **预改造**:「一次呈现」的状态收进一个模块。(01)
2. **`View` 成为唯一的页面身份**,内容指纹不再掺路径。(02)
3. **`Presentation`**:宿主签发身份,换一次呈现,旧的全部作废。(03)
4. **`Outcome` 拆成 `action` × `effect`**,念给模型的话逐字节不变。(04,解症状 4 的记录层)
5. **找不到目标时,等这一轮重试用尽再下结论**。(05a,解症状 3)
6. **派出的调用有侧栏执行,过期的调用有人告诉用户**。(06a,解症状 5)

**为什么读数排在工具循环之后。** 今天用户点击之后,引导唯一往前走的路是「触发器提交新表 → `page_changed` → 调模型」:`page_changed` 全仓只有这一个来源。读数的消费者是模型的 `observe` / `wait_for`,要到工具循环才有。先让触发器交出提交权,产品就会在两者之间停摆。

## Testing Decisions

**好的测试只断言外部行为。** 这次的外部行为是：模型看到了什么、归约器对输入给出什么状态与效果、页面上出现了什么、用户被告知了什么。**不断言内部调用顺序、不断言私有函数。**

**沿用现有四个接缝，不新增。**

| 断言什么 | 接缝 | 现有先例 |
|---|---|---|
| `View` 判定、`action`×`effect`、两个预算、结束方式、`Reading` 的吸收、`Presentation` 的作废判定 | 归约器 `step()`，纯对象进纯对象出 | 归约器测试文件，上百条用例 |
| 工具循环本身：`observe`→`point`→`done` 的序列、每步调用预算、修复轮只走一次不成环 | Agent 门面加一个假 provider | 运行循环测试文件，已经在数真正发出的请求数、分失败类型 |
| `act` 未注册、RPC 无执行动词、禁用动词零出现 | AST 架构守卫 | 架构守卫测试文件，每条都带「范围非空 + 判据在树上命中」的自检 |
| 接线（真 MV3 装载） | e2e 冒烟 | 现有冒烟脚本，真实 Chrome for Testing |

**`Actionability` 拆成策略与读数**（用户定）。单测跑在 node 环境，没有 `requestAnimationFrame` 也没有 `getBoundingClientRect`，所以：

- **策略**（几帧算稳、等多久、超时产生什么读数）走端口注入，在 node 单测里钉死——「超时只产生读数」这条规则要钉的正是策略。
- **真实的 bounding box 读取**只在 e2e 里证明接线。
- 这沿用仓库已有的拆法：页面问答那一处的头注释已经写明「不是纯模块的那部分…改由 e2e 证明」，本规格照同一条线切。

**五个症状各要一条今天会红的测试。** 每条都从真机记录里取输入形状（例如站内搜索换关键词而控件相同、目标短暂消失又回来、同页展开、结束时仍有调用在途），先证明它在现有代码上红，再证明改完绿。

**模型输入的冻结快照重新生成**（用户定）：守卫保留，作为倒数第二张票重录。它的价值是「以后再动模型输入时会红」，这次是有意要改，改完重录即可；上一次 pass 第 01 张票定的方法论保留，产物作废。

**每张票的验收**：类型检查 0、单测全绿、e2e 全绿、抽取器评测不退步。

## Out of Scope

- **代劳模式。** 三条开启条件写在 `CONTEXT.md` 的 `Tool` 注记里，任一条不满足就不开。
- **到达判据在代劳模式下的重新定义**——判据里「最后一步指着哪里」预设了那一步由用户执行，等开代劳时再改。指路模式下判据**保持不变**。
- **重录 Decision eval 语料。** 两批冻结语料（123 条与 31 条）在这次之后不可比，这是主动接受的成本；重录发生在模型输入稳定之后，不在本规格内。
- **`Workflow`、`Memory`、由模型按需读 `Skill` 全文**——`Plugin` 接缝不受本规格影响。
- **判断 SPA 是否渲染完成。** 没有可靠信号，骨架屏尤其：先换骨架再填内容时，地标结构已经变了，任何结构指纹都会认为新视图到了。
- **验证剪贴板是否真的写入。** `done` 的「某一步已完成」永远只是模型的声称。
- 新增 `observe` / `wait_for` / `read_doc` 之外的工具。
