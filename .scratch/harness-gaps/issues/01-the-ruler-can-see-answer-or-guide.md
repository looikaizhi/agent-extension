# 01 — 让尺子量得到「该指路还是该回答」

**What to build:**

决策 eval 的合法意图是 `['point','done','ask','read_doc']`（[annotations.ts:14](../../../evals/decision/annotations.ts)、[score.ts:21](../../../evals/decision/score.ts)）——**`explain` 不在里面**。于是「该指路还是该回答」这个判断完全在度量之外，而这正是 2026-09-21 在 bright.cn 上出问题的那个判断。

接下来要按客户需求大量改提示词，而提示词改动是互相干扰的：为了让「我要怎么打开看到这些产品呢」走 `point` 而松动 `done` 里那条「问怎么做就别替他执行」，很可能把它本来在防的那个错（问收费规则却被带去购买页）放回来。**没有尺子，这种事看不见。**

**Status:** done — 2026-09-22

---

## 要做的

1. **`explain` 成为一等意图**：类型、合法意图集合、标注页的选项。
2. **`pointedAt` 覆盖 explain 的 refs**（[score.ts:75](../../../evals/decision/score.ts)）。它现在 `default: return []`——explain 框出来的依据**会画在用户页面上**，和 `point` 的 ref 一样有「指到表外」「指到敏感控件」的风险，而闸门的零容忍计数此刻完全看不到它们。
3. **一个把真实世界撞见的一句话录成决策状态的小工具**（`evals/decision/record.mjs`）：给一个网址和一句话，跑一次真机，按语料的行格式写出来（`kind:'header'` + `kind:'call'`，[corpus.ts:77](../../../evals/decision/corpus.ts) 消费的就是这两种行）。
   > 为什么不复用任务 eval 来录：任务 eval 的到达判据里没有「答案就是终点」这种结局（`LastStep` 只有 done/step/none，[arrival.ts:13](../../../evals/task/arrival.ts)）。为了录几条状态去扩到达模型，是把两件事搅在一起。录制器还有个长期好处：**以后任何一次真实世界里的错判，都能当场变成语料一条**。
4. **录一小批问句形状的状态**，两类都要：
   - 本该 `explain` 的（真的在问这一页上的东西）；
   - **本该 `point` 却容易被当成问句的**（bright.cn 那条「那我要怎么打开看到这些产品呢」）。
5. **你来标**：我生成标注页并交给你，标完我拉回 `annotations.json`。
6. **基线**：新批次纳入，跑一遍 `eval:decision`，把闸门跑通。

- [x] **bright.cn 那条状态在语料里** —— 而尺子照出来的东西和预期不同，见下

## 续（2026-09-23）：把尺子合起来，它才有刻度

上面留下的那条「只有 3 条、统计力量很弱」，这一轮补掉了大半——**不是靠多标，是靠合并**。

- **`--corpus` / `--annotations` 现在都可以给多份**（`run.mjs`、`pull-annotations.mjs`）。语料是一批批长出来的，一批一个文件、一批一份标注；尺子只有合起来用才有刻度，而闸门本来就是在「两边共有的、有标注的状态」上比的。（pull 那边尤其必要：标注页的数据库里同时存着好几批，只给一份语料会把别批的标注判成「这批语料里没有这个状态」而整批失败。）
- **合并基线跑出来了**：126 个状态 × 3 遍。

  | | 只有 3 条时 | 126 条 |
  | --- | --- | --- |
  | 意图准确率 | 88.9%（区间 54–98%） | **82.3%（区间 76.6–86.8%）** |
  | 第一步准确率 | 33.3% | 74.1% |
  | 稳定性 | 稳定对 1 / 时对时错 2 | **稳定对 73 / 稳定错 15 / 时对时错 38** |

  **126 条里有 38 条是「时对时错」**——三成的状态在掷硬币。这和我在那 3 条上看到的是同一件事，现在有了规模。pass^3 只有 0.579。

- **旧基线已经废了，换掉了**：`t13-baseline` 的解析失败率是 **67.2%**（它早于工具调用那次重写）。闸门一直在跟一个没有意义的对照比——每次都以压倒性优势「通过」，也就等于什么都没量。现在 `baseline.json` 指向 `merged-baseline`，并在 `run.mjs` 的注释里写清了为什么。

- **又录了 8 条**（batch-3）：四条「怎么…／在哪」但其实要被带路的，三条真的在问这一页上的东西，一条祈使句做对照。标注页已更新到同一个链接，**等用户标**。录制用的原始日志随手清掉了——状态需要的东西语料里都自带。

## 续二（2026-09-23）：八条标完，闸门第一次量到了「没有变化」长什么样

- **11 条录制语料全部标完**（batch-2 的 3 条 + batch-3 的 8 条），并进 `annotations-recorded.json`（`annotations-batch-2.json` 随之删掉，不留重复的那一份）。
- **新基线 `merged-2`**：134 个状态 × 3 遍。意图准确率 **83.3%**（区间 77.7–87.8），第一步 79.8%，pass^3 0.634，**稳定对 85 / 稳定错 14 / 时对时错 35**。
- **最有价值的一条是闸门自己给出的**：`merged-2` 对 `merged-baseline`（同一份代码、只隔一次运行），意图准确率差 **+1.3pp，95% 区间 −2.4pp 到 +5.0pp**。
  > 这就是这把尺子的**噪声底**：±3pp 以内的变化说明不了任何事。以后改提示词，落在这个区间里就是「没量出差别」，不是「变好了一点」。没有这条，任何一次小幅改善都会被当成战果。

## 收尾（用户决定）

- **只留标过的 3 条**，另外 10 条连同录制的原始日志一起删掉（2026-09-22，用户：「剩余的不需要执行，把那部分的测试删除」）。语料 `batch-2.ndjson` 3 条，标注 3 条，基线 `runs/2026-09-22T07-04-00`：意图准确率 88.9%，稳定对 1、时对时错 2。
- 所以**这批的统计力量很弱**（95% 区间 54%–98%）：它足以把 09-21 那个错钉在版上、足以在意图回归时开火，但还不能用来判「改动是不是让整体变好了」。要那种判断，语料得随真实使用长大——录制器就是为此留下的。
- 批次之间没有合并：闸门只在「共有的、有标注的状态」上比较，所以 batch-2 有自己的基线，和 t13-baseline 互不相干。

## 一处失手（记在这里，免得再犯）

删那 10 份录制时用了 `for k in $KEEP`，而 zsh **不对未加引号的变量做分词**，于是一条都没匹配上，13 份原始 run 日志全被删掉——包括本该留下的 3 份。**语料文件完好**（状态需要的东西它都自带：上下文、模型当时读到的字节、当时的回答），所以丢的只是中间产物，下游一切照常。教训：在 zsh 里遍历列表要用数组，或者干脆用 node 写。
