# 04 — 这条对话装着什么，装多久

**What to build:**

四件事写在一张票里，因为它们是同一个问题的四个面：**这条对话到底装着什么、什么会过线、模型能看见其中多少**。

**Blocked by:** 03

**Status:** done — 2026-09-22（四层）

---

## 量到的事实

**一、对话没有上限。** `append` 只往后加，没有任何裁剪（[entries.ts](../../../src/agent/conversation/entries.ts)）。每次 `GET_CONVERSATION` 把**整条对话**过一遍线，而有事情进行时侧栏每两秒拉一次。一条长会话里，这个量只会单调增长。

**二、写入没有保护。** `chrome.storage.session.set` 裸调（[conversation-store.ts](../../../src/host/conversation-store.ts)）。配额一满就抛，那条记录**静默丢失**——而记录是「发生过的事」，丢了就没了。

**三、模型看不见上一轮。** 一次 `explain` 落地而这一趟没指过步，就记作 `answered` 收场（[machine.ts:261](../../../src/agent/thread/machine.ts)）。所以**每一句话都是一趟互不相干的运行**：`history.done` 只记「指过的步骤」，模型自己上一轮答过什么不在下一次调用里。2026-09-21 在 bright.cn 上，用户说「那我要怎么打开看到**这些产品**呢」，而「这些产品」在提示词里没有任何指代对象——模型只能从页面重新推断，于是把上一轮说过的两个入口又解释了一遍。

**四、跨趟没有记忆。** 一个标签页关掉，这条对话就没了（`conv:tab-<id>` 在 `storage.session`）。用户在同一个站点上第二次问同一类问题，产品什么都不记得。

## 为什么是一张票

因为**定上限之前，得先知道模型要看见什么**。

- 如果模型只需要看见「这一趟指过的步骤」（今天这样），那对话就是纯展示物，可以放心按条数裁。
- 如果模型要能续上一轮（第三条），对话就同时是**模型的上下文来源**，裁剪就成了「它能记得多久」，那是产品决定，不是性能调优。
- 而记忆（第四条）决定这份上下文活多久、存在哪：`storage.session` 随标签页死，`storage.local` 跨会话活着，但那是另一套配额和另一套隐私考量。

先裁后想，就会把第一版的裁剪规则整个推倒重来。

## 动手前要定的

1. **模型该看见上一轮的什么？** 它自己说过的话全文、还是一句摘要、还是只记「问过什么」？（每多一份，每次调用都要多花 token。）
2. **一次 `explain` 收场是对的吗？** 今天「一趟」等于「一次问答」。如果对话要连贯，单位可能该是「这条对话」而不是「这一趟」——那会动到 `Question` 的定义（CONTEXT.md）与 Run record 的边界。
3. **记忆的粒度**：跨标签页？跨站点？跨会话？用户能不能看见和删掉？（这是要写进产品说明的东西，不只是实现。）
4. **上限按什么裁**：条数、字节、还是「最近 N 轮 + 更早的摘要」？裁掉的东西在界面上留不留痕？
5. **写入失败之后怎么办**：丢一条记录和丢一整条对话，用户感受完全不同；配额压力下先牺牲谁？

## 建议的分层

1. **写入保护**先做——它独立于上面所有决定，而且现在是静默失败。
2. **上下文**（第三条）是质量天花板，值得单独一轮设计。
3. **上限**跟着上下文的结论走。
4. **记忆**最后，并且要先有产品决定。

## 进度记录（2026-09-22）

### 第一层：写入保护 ✅

`chrome.storage.session.set` 从前是裸调的。它一抛，不只是丢一条记录——宿主有**十三处** `await` 这个写入，整条渲染路径会断在那里，而且没有任何痕迹。

现在：**宁可丢掉最早的几条，也不丢刚发生的那条**。写不下就先扔一半再试，还不行只留最近 10 条，扔了几条记在 `Conversation.dropped` 上（界面显示「更早的 N 条已不再保留」）；真的一条都写不下，`writesFailing(tabId)` 为真，视图带 `storageFull`，界面说「刚刚发生的事没能记下来」——不假装写成功。异常不再穿到调用方。

> 为什么是「扔最早的」：记录是发生过的事，而用户正在看的是刚发生的那几条。

### 第二层：上下文 ✅（按用户 2026-09-22 的决定）

**决定一：模型看见最近几轮的原话**（用户说的 + 它自己答的），不是摘要。
**决定二：不改「一趟」的边界**——explain 落地仍然收场，只是新的一趟开始时多带一段上文。

实现走的是站点 Skill 那条现成的缝：宿主在派出调用时把上文交进去（`GuideEffectDeps.recent`），agent 层与 reducer 都不碰 `chrome.*`。选句规则 `recentTalk` 是纯函数：只要两边说过的话（`said`/`answer`/`ask`），**不要**指过的步骤（它们连同结局已经在 `history` 里）和宿主的 note（那是记账）；**不要**这一趟自己那句（消息末尾已经写着它）；最近 3 轮，每句最多 300 字。

代价：一轮答复百来个 token，而一张元素表起步四千——连贯性是个零头。

### 第三层：上限 ✅

真正的代价不是存储，是**每两秒拉一次整条对话**。所以**不删任何东西，只限制过线的量**：一次拉取带最近 80 条，视图上的 `earlier` 说清更早还有多少（界面：「更早还有 N 条，没有载入」）。实测跑完整套 e2e 后：存 125 条、带 80 条、更早 45 条。

### 第四层：记忆 ✅（按用户 2026-09-22 的决定）

**决定一：先记「这个站点上走通过的路」。决定二：用户看得见也删得掉。**

关键的发现是**不必新存一份数据**：`Run record` 一直在写（目标、最后落在哪一页、走过哪几步），只是从来没有人读它。所以这一层是「把已经有的东西读出来」，不是「再攒一份」。

- 只算**走通了的**：`ending === 'model_done'` 且确实走过步骤——「东西本来就在这一页上」不是一条路。
- 按站点匹配，最近三条，每条最多三步，写成**线索**而不是指令：明说「页面可能已经变了，照样对着这一页自己判断」。
- 它是第二个 `Plugin`（`memory`，默认开），所以有自己的开关，而且**每一趟的记录里写明它当时开没开**——「带记忆 / 不带记忆」可以分别度量，不是一笔糊涂账。
- 侧栏「它记住的路」列出每一条（目标 · 站点 · 步骤），可以单条忘掉，也可以全部忘掉。**忘掉就是把那条 Run record 删了**，不留影子副本。

e2e 实证：

```
这个站点上，以前在这台浏览器上走通过这些（只是线索，页面可能已经变了——照样对着这一页自己判断）：
- 「再带我去一页（04）」：Home
- 「带我去另一页（04）」：Home
```
忘掉一条就真的少一条；全部忘掉之后，提示词里那一段也跟着没了。

**留下的一个已知边界**：按「记录最后落在的那一页」的域名匹配站点。一趟从代码托管站走到文档站，只会记在终点那个站名下；要按起点匹配，得先把起始页也记进 `Run record`。

### 顺带发现：e2e 变偶发了

连跑多轮，每轮大约红一条，**位置每次都不同**（检视悬停、遮挡读数、Run record 的 Plugin、搬家后的对话）。其中「搬家」那两条已确认是我写的竞态——等到线程就断言，而对话是在那之后一步才搬的，已修。其余几条的证据还不够，已经把 Run record 那条的诊断信息补足（现在会打印每条记录的目标、步数、结局）。**一个偶发的套件等于没有套件**，这件事该单独开一张票。
