# 02 — 调用失败之后要有下文

**What to build:**

`retryable` 从侧栏一路带回宿主（[effects.ts](../../../src/entrypoints/sidepanel/effects.ts)、`EffectOutcome`），**却没有任何人消费它**：失败就写一条「调用失败：…」的 note，这一步关掉，等下一条读数（[machine.ts:190](../../../src/entrypoints/background.ts)）。既没有重试，侧栏上也没有任何重试入口。

网络抖一下 = 这一趟停在那里。用户得自己再打一遍字才续得上——而他多半不知道要这么做，只会觉得「这东西坏了」。

**Blocked by:** 01

**Status:** done — 2026-09-22

## 先要查清的一件事

侧栏里的 Provider 已经有流式超时与退避（CONTEXT.md `Panel`：「长达 60 秒的退避」）。**动手前先确认它到底重试到什么程度**——如果传输层已经重试过了，宿主再自动重试就是重复花钱；那样的话这张票就只做用户那一侧的入口。

## 修法（待上面确认后定稿）

- `retryable` 真的分支：能重的失败和不能重的失败，给用户的下文不一样。
- 一个**重试入口**：失败那条记录上就能点，不必重打一遍字。它走宿主已有的「再问一次」那条路（`askAgain`），不是新开一趟——原来的目标、走过的步骤都还在。
- 不能重的失败（配额、鉴权、模型输出被拒）不给重试按钮，给的是说明。

## 验收

- [x] 一次可重试的失败之后，用户点一下就能接着走，目标与已走步骤不丢
- [x] 不可重试的失败不给重试入口
- [x] 不重复重试：传输层根本不重试（见下），所以宿主这一次是唯一的一次
- [x] 类型检查 0，单测 1003、e2e 274/274 全绿

## 进度记录（2026-09-22）

- **先查清的那件事**：`complete()` **自己从不重试**——provider.ts 的注释写着「that decision belongs to the caller」。而 runner 如实算出 `retryable`，注释里甚至自嘲「a `retryable: true` nobody read」。所以不存在重复重试，宿主这一层是唯一的一层。
- **两档**：同一步里第一次传输层失败**自动原样再问一次**（不打扰用户），连着第二次才写 note，并在那条记录上带 `canRetry`，侧栏据此显示「再试一次」。它走的是已有的 `askAgain`，不是新开一趟——目标、走过的步骤、读到的东西都还在。
- **一个边界是测试逼出来的**：这一步的调用预算已经用完时不再自动重试。否则 `askAgain` 会撞上 `STEP_CALLS` 的闸，用户看到的是「这一步我已经想了 4 次」——把真正的原因（这一趟根本没走通）吞掉了。
- **计数放在哪**：`ThreadState.transportFails`，只在 `handleEffectResult` 一个函数里读写（任何回得来的结果都清零），所以不会和别处的「一步」边界走散。
- 协议加了一个动词 `RETRY_GUIDE`；对话条目加了 `canRetry`。
- e2e 改写了「调用过期之后结果才回来」那一段：原来断言用户当场被告知「调用超时」，现在断言**第一次原样再问、第二次才告知**，并新增一条「点按钮真的会再问一次」。
