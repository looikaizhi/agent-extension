## 已经看出来的形状

- **两条已修的，都是「链条中间取样」**：断言等到了链条上的第一环，就去读第三环。这类错在测试里和在产品里长得一模一样——上面那条产品缺陷就是同一个形状。
- **剩下的几条要么和时间有关，要么和机器负载有关**。那一条 `68.6ms` 的护栏最直白：它量的是真实耗时，三个 Chrome 连着跑的时候必然会飘。
- 套件现在有 279 条检查、一轮三四分钟。**红得越稀，越难抓**——这正是需要先把「怎么复现」做出来的那一类问题。

## 做了什么（2026-09-23）

### 一、两条常驻命令

- **`node tests/e2e/flaky.mjs [轮数]`** —— 跑 N 轮，把「哪条检查红了几轮、每次详情是什么」汇成一张表。偶发一轮看不出来，手工数六轮又慢又记不住；这条命令把它变成可复现的东西。
  > 一个教训：**聚合跑着的时候不要改 smoke.mjs**。第一次跑基线时我边跑边改，第 5 轮直接「没跑完」。
- **`node tests/e2e/sleeps.mjs`** —— 把「睡一个固定毫秒数，然后直接读状态」的地方列出来（后面跟着会轮询的读取不算）。当前：75 处固定等待，其中 40 处属于候选。这一类要**可见**，否则修完还会长回来。

### 二、按类修，不逐条打补丁

这一类的形状是同一个：**等到链条上的第一环，就去读第三环**。送出请求 ≠ 结果回来 ≠ 线程写完 ≠ 记录落盘。已经按这个形状改掉七处：

| 处 | 原来等的 | 现在等的 |
| --- | --- | --- |
| 搬家后的对话 ×2 | 线程搬过去了 | 对话也到了 / 新页真的被问了 |
| Run record 的 Plugin | 请求发出去了 + 400ms | 那一步真的落到线程上 |
| 运行结束即落盘 ×2 | 请求发出去了 + 600ms | 这一趟自己结束了（线程没了） |
| 06b 遮挡读数 | 之后的**第一条**请求 | 那条原因**到达了模型**（塞按钮本身会先引发一次结构变化的调用） |
| 刷新后游标不动 | 刷新 + 1200ms | 那一步重新画上了 |
| 用户去了别处 | 跳转 + 1500ms | 新页面上那一步画出来了 |
| 结束引导后键没了 | 300ms | 键真的没了 |
| trace 开关 / 结束 | 400ms、300ms | 调用落地 / 结束生效 |

顺带修掉一个**真缺陷**（不是测试的问题）：前台新建的标签页，激活与加载完成会撞在一起，`onUpdated` 手里的 `tab.active` 可能还是旧的，于是「切过去才跟」和「加载完再跟」两条路都不接它。

### 三、修完的测量

`node tests/e2e/flaky.mjs 5` → **5 轮全部 284/284，没有一条红过**。

诚实地说一句：五轮不是证明。之前最频繁的那条是三轮红一次，按这个频率，五轮全绿本身大约有 13% 的概率是运气。真正的依据是**每一条都查到了原因并对症改掉**，这张表只是没有推翻它。往后每隔一阵跑一次 `flaky.mjs`，比一次跑二十轮更有用——偶发是会长回来的。

### 三之二、还没动的

- **抽取耗时 <50ms 那条护栏**：它量的是真实耗时，三个 Chrome 连着跑必然飘。要么按机器校准，要么只在专门的一轮里跑——还没定。
- `sleeps.mjs` 列出的另外 30 多处：没有红过，先不动。**别把偶发当噪音关掉**，反过来也别把没红过的东西乱改成看起来更稳。
