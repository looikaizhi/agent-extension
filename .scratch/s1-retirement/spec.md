# S1 退场：让 Thread 只有一个所有者

> **修订记录。** 初稿经外部审核后重写。审核确认了主方向，并指出四条会造成行为回归的阻塞缺口与七条删除范围遗漏，本文全部采纳——逐条核实过，其中一条（固定计划会花模型调用）是初稿撰写期间新加的代码自己埋下的。原稿的九张票在此重排为十二张。

## Problem Statement

**对使用者：** 引导有时会「被上一次引导吃掉」。模型说完「看起来已经到了」之后，这一趟的 Thread 并没有真的结束——它只是被标成完成，记录留在原地。用户接着在同一个标签页发起一条 Pack 驱动的引导，浮层出来了，但点击被那条已经结束的 Thread 接走。同一个用户还会遇到：正常走完一趟之后不去点「结束引导」，这趟就没有任何 Run record 落盘；关掉浮层或直接关掉标签页时，在途的模型调用不会停，那是真金白银。配额用尽、跨站凭据安全停止、循环兜底这三种结束方式同样留下残骸。

**对读这个仓库的人：** 读不出「这个 agent 由什么组成」。仓库里同时住着两套引导实现，共用同一批入口事件，而它们的分界线从没被写进词汇表——`Thread` 只有一个条目，写着「每个标签页至多一个」，而事实上两个键空间各存一条。「先落盘、再删线程」这条规则早就写在代码注释里，却只有五个终态里的一个执行它。守着这一切的架构断言有一条是假绿：它的正则匹配不到任何真实的 import 行，被它点名的那个模块甚至从不调用它声称在守护的函数。

## Solution

**只留一个 Thread 所有者。** 模型驱动的那一套（纯归约器 + Effect 协议）留下；旧的那一套（`AgentHost`，Pack 流程与本地词法候选排序驱动）整套退场。

退场之后：

- **一个键空间。** 事件路由不再需要在两个所有者之间挑，`onOwner` 这条判断连同它守护的旧键空间一起消失。
- **一个终结流程，由状态转换驱动而非由入口驱动。** 判据是「这一次转换把 `status` 从 `active` 变成了非 `active`」——五种终态（模型说完成、两种配额耗尽、跨站凭据安全停止、循环兜底）加上三种外部结束（显式结束、关浮层、关标签页）全部汇进同一处。它是幂等的：一个 Thread 只终结一次，终结之后迟到的 Effect 结果不能把它写回来。
- **检视器点行起引导仍在，而且明确是「固定计划」。** 归约器新增一种计划来源，它耗尽时直接结束，**永不**发起模型调用——包括在等待窗口关闭之后。
- **Pack 只提供站点知识。** `siteNotes` 留下（真机上唯一被证明能改变模型行为的那半），可执行的 Pack 流程连同它的类型、线上协议字段、内容脚本的产出与面板的展示一起删。
- **「跳过」这个按钮不再骗人。** 它在模型驱动的引导下是空操作，删掉或明确说明，二选一。
- **词汇表成为唯一的事实源。** 决策记录目录整个删除，其中还没有等价记录的事实并进词汇表。所有指向已不存在文档的引用——包括裸文件名引用与决策记录编号引用两种形态——一次性改指或删除，并由一条守卫保证这类腐烂以后必须在测试里红。

## User Stories

1. 作为扩展的使用者，我希望模型说「已经到了」之后这一趟就真的结束，这样我接着发起的下一条引导不会被上一趟接走点击。
2. 作为扩展的使用者，我希望配额用尽而停下的那一趟也真的结束，这样它不会以「还活着」的样子挡住我的下一趟。
3. 作为扩展的使用者，我希望因为跨站页面要密码而停下的那一趟也真的结束，这样一次安全停止不会留下半条活着的引导。
4. 作为扩展的使用者，我希望引导因为原地打转被拦下时也真的结束，这样它不会一边说「已经停下」一边继续规划。
5. 作为扩展的使用者，我希望正常走完一趟引导之后这趟的摘要就已经落盘，这样我不必为了留下记录而额外点一次「结束引导」。
6. 作为扩展的使用者，我希望关掉浮层时在途的模型调用被取消，这样我不会为一次我已经放弃的引导付钱。
7. 作为扩展的使用者，我希望关掉标签页时这一趟的持久状态被清干净，这样同一个标签页 id 复用时不会捡到上一趟的残留。
8. 作为扩展的使用者，我希望同时触发两种结束（比如模型刚说完成、我又点了结束引导）时不会留下两条运行记录，这样我的记录是可信的。
9. 作为扩展的使用者，我希望一趟引导结束之后不会因为一个迟到的模型结果而「复活」，这样结束就是结束。
10. 作为扩展的使用者，我希望摘要写不进去的时候引导仍然结束、并且明确告诉我摘要没保存，这样我不会以为它还在跑。
11. 作为扩展的使用者，我希望在检视器里点一行仍然能起一条引导，这样这次清理不拿走我已经在用的能力。
12. 作为扩展的使用者，我希望检视器起的那条单步引导**不花任何模型调用**，包括我盯着它不动、等待窗口关闭之后，这样「零成本」这个承诺是真的。
13. 作为扩展的使用者，我希望页面问答覆盖引导之后仍然能回到引导，这样问答不是一条单向门。
14. 作为扩展的使用者，我希望浮层上的「跳过」要么真的能跳过、要么根本不出现，这样我不会以为按钮坏了。
15. 作为没有配置模型的使用者，我希望产品明确告诉我「引导需要先配置模型」，这样我不会对着一个静默失败的按钮猜。
16. 作为读这个仓库的人，我希望「一次多步引导的持久状态」只有一个实现，这样我读一处就读懂了它。
17. 作为读这个仓库的人，我希望词汇表里 `Thread` 那句「每个标签页至多一个」是真的，这样词汇表可以被信任。
18. 作为读这个仓库的人，我希望「一趟引导结束时要做什么」写在一个地方、由一个判据触发，这样我加一种新的终态时不必去八个调用点各补一遍。
19. 作为读这个仓库的人，我希望宿主进程的入口文件里只剩平台调用的接线，这样我读它是在读接线而不是在读判断。
20. 作为读这个仓库的人，我希望纯归约器不再从被它取代的那条路借类型，这样依赖方向只有一个。
21. 作为读这个仓库的人，我希望源码里不存在只被测试调用的判断函数，这样「有测试」不再等于「有人在用」。
22. 作为读这个仓库的人，我希望注释里引用的每一份文档都能被打开，这样注释里的知识指得到地方。
23. 作为读这个仓库的人，我希望花钱测出来的事实住在词汇表里而不是一个会被整批删掉的目录里，这样它们不会随目录一起消失。
24. 作为读这个仓库的人，我希望设计文档与教程文档不再描述一套已经不存在的实现，这样「唯一事实源」不是一句空话。
25. 作为维护这个仓库的人，我希望架构断言在源码上至少匹配到一处，这样「匹配不到」不会永远表现为绿灯。
26. 作为维护这个仓库的人，我希望架构断言检查的是「谁调用了归约器」而不是「谁 import 了它」，这样一个 type-only 的 import 不能满足它。
27. 作为维护这个仓库的人，我希望「一趟引导结束」这件事有单元测试，这样它不再只能靠一次浏览器全流程或一次二十分钟的真机验证。
28. 作为维护这个仓库的人，我希望删除的完整性由一份明确的源码扫描清单来证明，而不是只靠类型检查，这样不会留下没人引用的旧模块、旧协议字段或死路由。
29. 作为维护这个仓库的人，我希望 Pack 的类型、线上协议与面板文案里不再有没有读者的东西，这样它们描述的是真的存在的能力。
30. 作为未来做架构体检的人，我希望「为什么删掉了本地词法候选排序」被记下来，这样我不会把它当成缺失的能力重新提出来。
31. 作为未来做架构体检的人，我希望「为什么两套实现只留一套」被记下来，这样我不会把统一它们再提一遍。
32. 作为使用真机脚本量测的人，我希望每轮之间的清理不再依赖脚本显式调用「结束引导」，这样脚本的收工方式不再是产品行为的一部分。

## Implementation Decisions

### 1. 终结由状态转换驱动，不由入口驱动

**判据只有一条：这一次归约把 `status` 从 `active` 变成了非 `active`。** 满足它就进入统一终结流程，做四件事：中止在途 Effect、落盘 Run record、删 Thread、通知外部世界（清浮层 + 广播）。

**这条判据覆盖的终态有五种**——模型说完成、模型调用配额耗尽、文档抓取配额耗尽、跨站凭据安全停止、循环兜底。初稿只列了第一种，其余四种会留下记录，这是审核指出的阻塞项之一。

另外三种结束来自归约器之外（显式结束引导、用户关浮层、用户关标签页），它们调同一个终结流程。

**顺序不可换**：Run record 必须在删 Thread 之前写——那是这趟运行最后一次还存在、可被记录的时刻。这条规则今天已经写在代码注释里，这次是把它从一个调用点的约定变成一处职责。

### 2. 终结必须幂等，且不可被迟到的结果复活

MV3 的多个监听器并发执行，以下竞争都真实存在：模型说完成与用户点结束同时发生；关浮层与关标签页同时发生；一个 `effect_result` 已经读到旧 Thread，终结流程随后把它删掉，结果处理又把它写回来。

因此终结流程必须保证：

- **一个 Thread 只终结一次。** 重复调用是无操作，不重复写 Run record、不重复广播。
- **终结之后任何写入都不能重建它。** 迟到的 Effect 结果必须被识别为「针对一条已经结束的 Thread」并丢弃。
- **Run record 写失败不阻断终结。** 仍然删 Thread、仍然中止 Effect，并把失败明确告诉用户——记录丢了比引导卡死轻。

现有的串行队列只包住重规划一条路径，`applyGuideInput` 与终结流程都在队列之外。**复用同一个按键串行的队列，把范围扩到所有状态写入**，而不是新造一套机制。

### 3. 归约器新增「固定计划」，且它永不调用模型

检视器交来的是一串已经写好的 `GuideStep`，它们携带的是 `Descriptor`（跨快照的持久身份），不是此刻的 `Binding`——**初稿把这两个词混为一谈，此处更正**：绑定发生在渲染器要画它的那一刻，不在计划产生的时候。

Thread 记录这趟计划的来源。固定计划与模型计划的分别是：

- 固定计划**耗尽时直接终结**（走第 1 条那条统一流程），绝不发起模型调用
- 这一点必须在**等待窗口关闭之后**依然成立。归约器当前在计划走到最后一步而页面没有变化时会重新规划一次——那条路径是为模型驱动的引导加的，对固定计划必须关闭。**这是初稿最严重的一处遗漏，而那段代码正是撰写初稿期间新加的。**

固定计划同样需要 `goal` 与 `table`：Thread 的状态要求前者，Run record 也写它；而侧栏今天发起这条引导时两样都没带，需要一并补上。

来自原型的形状（决定点在于第二种形态不产出模型调用，且带着计划来源）：

```
| { kind: 'start'; goal: string; table: PromptTable; effectId: string }
| { kind: 'start_fixed'; goal: string; table: PromptTable; steps: readonly GuideStep[] }
```

第二种形态没有 `effectId`，因为它不需要 Effect 预算——这一点本身就是它与模型驱动那条路的分界。

### 4. 旧实现退场，与问答迁移必须是一次原子切换

删除的是：旧宿主模块及其事件流接口、宿主入口里消费旧事件流的那个效果解释器、校验模块里 CL-3/CL-4 那一段（它的判据需要一个词法结果，而词法结果的唯一生产者随旧实现一起走）、以及路径选择模块及其测试。

**词法模块只部分退场。** 候选排序入口与其相关导出随旧宿主一起走——那是唯一的生产消费者。但**打分与 CJK 分词必须保留**：离线评测脚本用打分做「零模型下界」，那是其中一道门槛的一半，整个删掉会让评测直接红。

**同一批里必须一起完成的还有：** 检视器改走固定计划、问答的活跃判断与恢复改读唯一剩下的那个键空间、旧键空间退场、所有权路由删除、未配置模型时给出明确说明。

**不可拆的理由：** 端到端套件里有一条断言「手写步骤的零成本引导 + 问答之后仍可继续」。检视器先迁而问答后迁，这条断言在中间状态会红——**先迁一半不是「套件绿」，是「套件红」**。这是审核指出的第四条阻塞项。

**同时有一条架构断言的主语会消失**：它断言旧宿主模块的源码里不出现打分函数，而那个模块本身要被删。这条断言随之删除；它守的那件事（绑定不许打分排序）由同文件里另一条针对绑定模块的断言继续守着。

### 5. 删除的完整性靠源码扫描清单，不靠类型检查

类型检查开着严格模式但没开未使用检查，因此它能发现悬空 import，**不能**发现没人引用的旧模块、旧协议字段或死路由。删除验收必须给出一份明确的扫描清单（按符号名与协议字段名逐项确认零引用），并跑完整的验证与离线评测。**「类型检查零错即证明不留半条路」这句话不成立，初稿写错了。**

### 6. Pack 的删除面比初稿列的宽

除了流程类型与匹配函数，还必须同批处理：线上协议里承载 Pack 文本的字段、内容脚本产出该文本的调用、侧栏对它的展示与「写进引导包」文案、以及「本站可用引导包」这句——剩下的 Pack 已经不再提供引导流程，那句话会误导。相应的单元测试与端到端断言一并处理，词汇表里 `Pack` 的定义也要改写。

### 7. 「跳过」在模型驱动的引导下必须诚实

浮层无条件显示「跳过」按钮。旧实现退场之后所有引导都由模型驱动，而宿主对这条路的跳过是空操作——按钮点了什么也不发生，侧栏却记一笔「跳过」。

**注释解释不了这件事，用户看不到注释。** 二选一：删掉按钮，或让它给出可见的「这条引导不支持跳过」。本规格不发明新的跳过语义（那需要归约器能记住「别再提这个」，它今天没有），只要求按钮不骗人。

### 8. 架构断言改成断言调用点，并且自检

单写者断言从「谁 import 了归约器」改成「谁调用了它」。这次假绿的根因正是两者的差别：被点名的模块满足了 import 断言而一次都没调用。

同时给这条断言本身加一条前置断言：**它在当前源码上必须至少匹配到一处**。今天的失效形态是「匹配不到 → 断言集合为空 → 通过」，加上这一条之后同样的失效会红。

**审核建议改用编译器 AST 而非继续叠加正则。** 方向成立（正则识别不了 import 别名与命名空间调用），但本规格不在这一条上开先例——同一个测试文件里十几条断言全是源码正则扫描，只换一条会造出两套并存的守卫机制，正是这次重构要消灭的形状。AST 迁移单列为一张独立的票，整个文件一起迁，不阻塞本次任何工作。

### 9. 文档收敛的范围是三类引用，不是一类

初稿只算了裸文件名引用（十二个文件名、五十九处）。实际还有两类：

- **决策记录编号的文字引用**：三十二个文件、七十二处。删掉决策记录目录而不处理它们，等于用新形式重造一遍同样的腐烂。
- **仍在描述旧实现的长文档**：设计文档与教程文档各有若干处。它们不改写，「唯一事实源」就不成立。

守卫因此要查三样：裸文件名引用能否解析、决策记录编号引用能否解析、以及删除之后源码里不得再残留决策记录引用。

事实的迁移分两步：**先把事实复制进词汇表**（安全，随时可做），**再原子完成「改所有引用 + 改写旧文档 + 加守卫 + 删目录」**。顺序反过来会出现一段「事实已删、引用还在」的窗口。

要并进词汇表、目前没有等价记录的五条：宿主进程里网络请求超过三十秒会导致进程被终止（这是模型调用不在宿主进程的原因，而现有词条只说结果不说原因）；会话级存储只有宿主进程可写；归约器是纯的；出处扫描器是独立重写的第二实现且与解析器零函数共享；以及「一百三十九条端到端断言全绿而产品正门在真实网站上一次都没启动过」。

外加两条本次产生的：为什么删掉旧实现、以及本地词法**候选排序**部分退场（**不是整个词法模块**——初稿在这里自相矛盾，此处统一）。

## Testing Decisions

**好的测试只断言外部行为。** 唯一涉及内部顺序的是「Run record 在删 Thread 之前写」，而承接它的测试文件的既有夹具已经在记录存储调用顺序，所以顺序本身就是可观察的外部行为。

**新缝只有一个：** 宿主的引导 Effect 依赖对象增加一个 Run record 存储端口，终结流程成为一个可注入依赖驱动的函数。其余全部落在现有缝上。

| 断言什么 | 缝 | 现有 prior art |
|---|---|---|
| 五种归约器终态各自都触发终结，且落盘在删除之前 | 宿主引导 Effect 依赖对象 | 该测试文件已用内存存储驱动这个缝，并已记录调用顺序 |
| 重复终结是无操作；终结后迟到的结果不复活 Thread；Run record 写失败仍然终结并报告 | 同上 | 同上 |
| 三种外部结束都触发同一个终结流程 | 同上 | 同上 |
| 固定计划：落成步骤与游标、产出呈现、不发模型调用、不花预算 | 归约器 | 归约器测试文件，七十余条用例全部纯对象进纯对象出 |
| **固定计划在等待窗口关闭之后仍然零模型调用** | 归约器 | 同上；这是审核指出的必测项 |
| 单写者断言改成调用点，并且自检至少匹配一处 | 架构断言的源码扫描 | 同文件多条同形态断言 |
| 三类文档引用守卫 | 同上 | 同上 |
| 删除的完整性 | 明确的源码扫描清单 + 完整验证 + 离线评测 | 类型检查**不足以**证明，见实现决定第 5 条 |

**端到端只证明接线，不再证明逻辑。** 三种外部结束源自入口文件的平台监听器，端到端证明监听器接上了终结流程；流程本身做了什么由单元测试断言。这是宿主入口文件的单元覆盖从零变成有的第一步。

**要删的旧断言：** 端到端套件里针对旧实现路径选择的断言随实现一起删。那条「手写步骤的零成本引导 + 问答之后仍可继续」的断言**不删**，改为断言迁移之后的同一行为——它正是原子切换不可拆的证据。

**要加的端到端断言：** 三条，形状都是「发一条消息、读一次存储、断言键不在了且记录在」——模型终态之后、关浮层之后、关标签页之后。

## Out of Scope

- **决策评测**（量模型拿到 Element table 之后决定了什么）。架构评审列为最大缺口，但与本次的所有权收敛无关。
- **发明新的跳过语义。** 本次只要求按钮不骗人；让归约器记住「别再提这个」是另一件事。
- **入口文件里其余的重责任。** 它还有十几个消息分支、两个用户可见字符串、三个等待窗口常数没有测试。本次只搬走终结那一块。
- **一条线上消息承载六种含义且一律标红**，以及它缺少标签页过滤。已核实的独立缺陷，与所有权无关。
- **序列化与包裹分属两个模块导致的重复序列化**（同一张表每次引导调用序列化两遍，且随机数校验的是没有标记的那一份）。经审核确认当前不是已证实的绕过——两次序列化的差只是一个固定字面量——但接口不一致与重复开销是真的。另开。
- **词汇表里同一个概念的多份实现**（地点、控件身份投影、Effect 结果类型、世界快照类型）。已核实、值得做，但每一条跨越与本次不同的调用者集合。
- **契约里重复声明的枚举与 Intent 模块化。** 架构评审列为首推，拷问后改为最后评估：先收敛重复的枚举，不机械地「一种 Intent 一个文件」。
- **架构断言整体迁到编译器 AST。** 单列一张独立的票，不阻塞本次工作。

## Further Notes

**这是一次宽重构，不是垂直切片。** 爆炸半径主要落在宿主入口文件：它要删掉一个效果解释器、换掉一个键空间的三处读取、删掉所有权路由，而它**至今零单元测试**。

**关于「先补网再拆」这句话的更正。** 初稿写「三条端到端断言必须排在删除之前」——那三条今天全是红的（三种结束路径现在都不清理），当不了先补的网。正确的形状是每条断言与它的接线**同一张票**落地；真正的网是那条既有的「显式结束」端到端断言在整个过程中保持绿。

**关于原子切换。** 审核最有价值的一条判断是：检视器迁移与问答迁移不能分票。在不做兼容层的约束下，中间状态必然是坏的；与其让一张票的验收标准变成「套件红是预期的」，不如接受一张大票。

**这次改动不影响已经跑完的六轮真机测量。** 真机脚本每轮之间显式调用结束引导，而那正是今天唯一会删 Thread 的地方——那六轮数据是干净的。反过来说，脚本的收工方式今天是产品行为的一部分；这次改完之后它不再是。

**关于删掉决策记录目录这个决定本身。** 我在拷问过程中明确反对过一次，理由是其中三条各钉着一件重新学一遍要花真金白银的事；用户在看到「哪些事实已有等价记录、哪些没有」的核对结果之后重申了这个决定。核对结果写在实现决定第 9 条。这段记在这里，是为了让将来读到「为什么这个仓库没有决策记录目录」的人知道它不是遗漏。

**关于本规格自己被证伪过四次。** 撰写与审核期间，以下四条初稿判断被数据推翻：Pack 流程必须跟着旧实现死（实际只需六行映射即可迁移，用户在知情后仍选择删）；产出 Pack 文本的模块会跟着死（实际被内容脚本引用）；删掉决策记录会丢失元素表裁剪那条教训（实际词汇表记得更细）；词法模块整个删除（实际离线评测在用它的打分）。记在这里，是为了让实现者知道这份规格的每一条都应该被同样对待——**照着做之前先核实**。
