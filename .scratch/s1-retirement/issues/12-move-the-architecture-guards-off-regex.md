# 12 — 架构断言整体迁离正则（独立，不阻塞任何票）

**What to build:** 架构断言不再靠正则扫源码文本。今天它们识别不了 import 别名、命名空间调用与重导出，这次的假绿就是这种识别能力不足的一个实例。

**这张票独立存在，不阻塞本目录里的任何一张，也不被任何一张阻塞。** 它被单列出来是因为：外部审核建议把单写者那一条改用编译器 AST，而在一个十几条断言全是正则扫描的文件里只换一条，会造出两套并存的守卫机制——正是这次重构要消灭的形状。要迁就整个文件一起迁。

**Blocked by:** None — can start immediately

**Status:** done

- [x] 用项目已有的 TypeScript 编译器能力遍历源码，替代正则扫描
- [x] 能识别 import 别名、命名空间调用、重导出
- [x] 该文件里现有的每一条断言迁移后行为不变——迁移前后各跑一次，红绿结果逐条对齐
- [x] 每条断言保留「在当前源码上至少匹配到一处」的自检
- [x] `npm run verify` 全绿

## 验收记录

- 迁移前后各跑一次 `architecture.spec.ts` + `gates.spec.ts`，按测试标题逐条对比：原有 41 条结果完全一致（全部通过），新增 1 条（树上没有真实命中点的判据用合成违例证明存活）。
- 另用一个对照脚本把每条旧正则判据与新的语法树判据并排跑：21 条带作用范围的守卫在全树逐文件结果一致；`focus()` 计数、`effects.ts` 的两处 `sendMessage` / `fetchFn` / `credentials:'omit'`、`storage.sync` 等文件级检查一致；反向验证里 19 个合成违例两边都抓住、9 个干净样本两边都放行——**分歧 0**。
- 唯一一处结果变化出现在第一次迁移：请求体白名单改读 `JSON.stringify({…})` 的对象字面量后，一度把条件展开整体当作不可检查而判红。改为展开可见的条件展开之后转绿，并且第一次真正检查了展开里的 `tools` / `tool_choice` 等字段——旧的按缩进匹配从来没看到它们。
