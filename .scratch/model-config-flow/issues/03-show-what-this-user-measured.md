# 03 — 标出你自己验收过的那几个

**What to build:**

模型列表里，用户**自己在这个端点上验收过**的模型带着标记：`✅ 验收过` / `⚠️ 跑不动`；下面再单独列一行，点一下就切过去。

这是对「424 个模型里我该选哪个」的正面回答——**不靠产品预测，靠你自己量过的那几次**。

---

## 为什么这需要先改存储

01 和 02 之后，验收结果是 `ProviderConfig` 上的**一个** `forcedToolChoice`，而且「换模型 → 退回未知」。于是：

- 换一个模型试试，上一个量到的结论**当场丢掉**；
- 列表里因此**没有任何东西可显示**；
- 02 那个「关掉思考」的按钮修好过的模型，回头再选中它，又得重修一次。

所以 03 的第一件事是把它改成按模型存：`verdictByModel: Record<string, ForcedToolChoice>`，替掉那个单值字段（不留兼容层）。发前拦截（`runner.ts`）随之改成问**这一次调用要用的那个模型**——一个地址上既有认强制工具调用的模型、也有只会回文字的模型，按端点一刀切的闸门是没人过得去的。

### 两张表，不是一张

`requestByModel`（字段）和 `verdictByModel`（判决）**刻意不合并**，因为它们的寿命不一样：

| | 是什么 | 什么时候作废 |
|---|---|---|
| 字段 | **输入**（用户填的，或按钮试出来的） | 只有用户自己改它的时候 |
| 判决 | **测量**，而且它会拦下真实调用 | 换端点 / 换 Key / 换协议；以及这个模型的字段被改动时 |

换端点时字段**留着**：判决是「将会发生什么」的断言，过期了很危险；字段是输入，过期最多换来一次 400，而 02 已经给了走出那一次 400 的按钮。为一个 URL 打字失误就把手打的 JSON 清掉，是另一种伤害。

### 那张表只装量到过的东西

写「未知」= **把这一条删掉**，而不是存下 `'unknown'` 这个词。真机第一趟就撞到理由：`deepseek-reasoner` 那次是 503（端点忙），什么都没量出来，却在表里留下了一行看起来像结论的东西。出口按钮（「仍然按可用处理」）同理。`verdictFor` 对缺失的模型本来就答 `unknown`，所以两种写法行为上从来没差别——差的是这张表对自己装了什么诚不诚实。

## Out of Scope

- **替用户排序 / 推荐模型。** 标记只说「你量过，结果是这个」。哪个更好用不是这张表能回答的。
- **把量过的结果显示在对话里**（比如引导失败时提示「你验收过的另外两个模型可用」）。设置页先站住。
- **自动重验。** 端点忙过去之后没人知道该什么时候再试，用户点一下就是了。
