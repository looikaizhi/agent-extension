# 01 — 先连上，再挑模型

**What to build:**

用户只填**地址和 API Key**，点一下就拿到这个端点真有的模型列表；从列表里挑一个（也可以手打），再点一下就知道**这一个模型**能不能驱动本产品。

今天的表单是反的：它要求用户在我们还没跟端点说过一句话之前，先手打一个模型名。代价是实打实的——2026-09-25 对着一个聚合端点核过，仓库里 9 条预设的模型名有 **5 条已经不存在**（`moonshot-v1-*`、`glm-4-*`、`qwen-plus`/`qwen-turbo`、`openai/gpt-4o-mini`、`Qwen/Qwen2.5-7B-Instruct`）。模型名是端点的属性，问出来就不会过期。

**这一票不改协议层。** 01–08 那条缝一行不动，改的是设置面板与 `testConnection` 的形状。

---

## 一、必须是两步，不是一步

```
第 1 步「连接」   地址 + Key           → GET /models → 拿回候选列表
第 2 步「验收」   选定模型（可手填）    → 一次最小真调用 → 写回三态开关
```

> **为什么不能合成一次点击。** 第 2 段探测（08）是**对着某一个具体模型**发出去的真调用——模型还没选，它就无从发起。今天两段挤在一次点击里，只是因为模型是预先填好的；顺序一反，它们就必须分开。这不是额外工作，是流程本身要求的。

`testConnection` 因此拆成两个函数：取列表的那一段，和对着一个模型做真调用的那一段。两段仍然都经 `transport` 发出，全仓仍然只有两个联网点。

## 二、「在 `/models` 里」不等于「能用」

候选列表**只负责别让用户手打 424 个名字里的一个**，绝不负责「这个能用」。同一次核对（2026-09-25，`api.xty.app`，424 个模型）里，至少四类在列表里而用不了：

| 模型 | 在 `/models` | 真打 |
|---|---|---|
| `gemini-3-pro` | ✅ | 503 当前分组无可用渠道 |
| `gemini-2.5-flash` | ✅ | 500 回复为空 |
| `qwen3.8-max` | ✅ | **400**，除非加 `enable_thinking: false` |
| `gpt-6-astra` | ✅ | 能用，但首字节 13.3 / 16.2 / 16.4s，撞 `transport` 的 15s 连接钟 |
| 23 个图像 / 音频 / 向量模型 | ✅ | 根本没有工具调用 |

> **为什么这条要写进票里。** 一个只按 `/models` 填的下拉，会让用户从 424 个里挑一个，然后在引导跑到一半时撞上——**那正是第 08 张票刚刚消灭的失败模式**，不能在前端把它请回来。列表负责「别让他手打」，真调用负责「别让他选中一个跑不动的」，两者都要。

候选里过滤掉明显没有工具调用的那一类（名字含 embedding / rerank / tts / whisper / audio / image / video / dall-e 等）。**只过滤这一类**，别试图猜别的——猜不准的东西交给第 2 步去量。

## 三、预设换职责，但不能删

预设不再是模型名的来源，但它给的另外三样 `/models` 永远给不了：

- **端点地址本身**——新用户不知道 `https://api.deepseek.com/v1`；
- **那些必需的 `request` 字段**——实测：不加 `thinking: {type:'disabled'}`，DeepSeek 在强制工具调用上 400；不加 `enable_thinking: false`，通义也 400，而且两家的拼法互发都会 400；
- **协议**，以及 Ollama 那条 CORS 提示。

所以它变成「一键填好 URL + 协议 + 必需字段」的快捷方式。

## 四、协议仍然由用户说，不推断

`/models` 只给名字，不说这个端点讲哪种线格式。同一个聚合商同时服务 `/chat/completions`、`/responses`，以及另一个地址上的 `/v1/messages`；而且**同一个 `gpt-6-astra` 在两条线上都跑得动，首字节差一倍**（旧线 22.4s，新线 12.3s）。这件事没有办法自动探测出来。

## 五、三态开关要看得见、也要有出口（修一个死锁）

现在探测判成「不支持」就直接存进配置，而 06 的发前拦截会因此拒绝这个端点的**每一次**调用。但界面上：存下来的 `forcedToolChoice` 完全不渲染；那行结论是组件内的瞬时状态，面板一关就没了；用户**没有任何办法改回去**，只能改端点地址触发重置。

误判一次，这个端点就废了。

- 那一行改成从**存下来的** `forcedToolChoice` 渲染；
- 判成「不支持」时，旁边给一个「仍然按可用处理」，写回 `unknown`。

> **为什么要留这个出口而不是相信探测。** 三态的默认值是「未知＝照发」，理由是「还没问过，先按能用处理」。探测答错的时候，用户手上应该有同一个权利。

## 六、改了端点或 Key，列表和开关一起作废

跟现在「改端点就重置开关」是同一条理由：对 A 端点的判决不能粘在 B 端点上。模型候选列表同理——它也是上一个端点的东西。

## 实现记录

- `provider.ts`：`testConnection` 拆成 `listModels` + `verifyModel`，两段共用 `addressProblem()`（无地址 → 非法 URL → 缺 Key，按「哪句最具体」排序）。
- **只有真发出去过才写配置。** 第 2 步在地址不合法或模型没选时提前返回，面板据此不写 storage——否则一个打错的地址会被存下来，下次开面板又读回去。
- 文案跟着流程改了三处：`MODEL_NOT_CONFIGURED`（e2e 逐字比对那条也同步）、`runner.ts` 拦截时那句现在指向新的出口、面板挂载时那句不再说「未验证」而是报出存着的模型名。
- 顺带把面板挂载时的 `baseURL.includes('localhost')` 换成 `modelIsConfigured()`——跟宿主起跑前问的是同一条判据，面板不会再说宿主不认的「已配置」。

## Out of Scope

- ~~**多套 Provider 配置**~~ → **不做（2026-09-25 用户定）**。那个产品问题他答了：**配一个端点用到底**，在这一个端点上挑自己觉得合适的模型。所以 storage 结构和 `loadConfig` 的契约都不用动，这一票也不用开。
- ~~**Anthropic Messages 适配器**~~ → **跟着不做**。它本来是绑在多配置上的，而且**在「一个端点用到底」这个前提下它根本没有必要**：同一个 `api.xty.app/v1` 的 OpenAI 兼容线上就列着 20 个 `claude-*`（`.scratch/model-protocols/xty-models.md`「Anthropic · Claude（20）」），用户点「连接」就能看见、选上就能用；某一个具体的 claude 模型认不认「必须调用工具」，由第 2 步那次真调用当场量出来——这正是这条流程要干的事。
  （原生那条线仍然可达，实测记录留着备查：`https://claude.xty.app/v1/messages`，`x-api-key` 与 `Bearer` 都收，流式 + `tool_choice:{type:'any'}` 通，`tool_use` 与 `input_json_delta` 都在，首字节 0.8s。真要用它，得先有人要「两条线同时留着」——今天没有这个需求。）
- **能力矩阵界面。** 模型协议规格 D5 明说「只是一行字，不做能力矩阵界面」，这条继续有效。
- **自动探测每一个模型。** 424 个模型 424 次真调用，贵且没人要。
- **上下文窗口自动填。** `/models` 不给这个数据。
