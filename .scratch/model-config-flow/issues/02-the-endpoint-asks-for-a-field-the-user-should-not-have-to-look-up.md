# 02 — 端点要的那个字段，用户不必自己去查

**What to build:**

用户在自己那一个端点上挑中一个模型，点「验收」，撞上这堵墙：

```
The tool_choice parameter does not support being set to required or object in thinking mode
```

他看到的不该是这句英文，而是一句人话加一个按钮：

> **这个模型开着「思考模式」。本产品每次都要求模型必须调用一个函数，而它在思考模式下不接受这个要求。**
> 端点原话：`The tool_choice parameter does not support being set to required or object in thinking mode`
> 　**[ 关掉思考，再试一次 ]**

点一下，产品自己试出这个端点认哪种写法、记在这个模型名下、重跑一次验收，然后告诉他结果。**用户不需要知道 thinking 是什么，更不需要知道两家厂商的字段名拼得不一样。**

**这一票不改协议层，也不改 01 的两步流程**，它补的是第 2 步失败之后的那一半：今天验收只会把端点的原话原样吐出来，正确但无用——用户读完仍然不知道该做什么。

---

## 实测底账（2026-09-25，`https://api.xty.app/v1`，`/chat/completions`）

| 模型 | 不加任何字段 | 加 `enable_thinking:false` | 加 `thinking:{type:'disabled'}` |
|---|---|---|---|
| `qwen3.8-max` | **400** 思考模式拒收 | **200 ✅ 调用了工具** | **400**（同一句拒绝） |
| `qwen3.7-plus` | **400** 思考模式拒收 | — | — |
| `qwen3-235b-a22b-thinking-2507` | 200 ✅ | — | — |
| `deepseek-v3.2-thinking` | 200 ✅ | 200 ✅ | 200 ✅ |
| `deepseek-v4-pro` | 200 ✅ | — | — |
| `glm-5.3` | 200 ✅ | — | — |
| `gpt-6-sol` | 200 ✅ | **200 ✅** | **200 ✅** |
| `claude-sonnet-5` | 200 ✅ | **200 ✅** | — |
| `deepseek-reasoner` | **200，但没调用工具**（回了一段文字） | — | — |
| `qwen3-32b` / `qwen3-next-80b-a3b-thinking` / `deepseek-r1` | **429** 上游负载饱和 | — | — |

四条结论，全部来自上表：

1. **这堵墙很窄**：撞墙的是通义系的一部分，不是「所有带 thinking 的模型」。厂商文档里 DeepSeek 那条（2026-09-14 在 `api.deepseek.com` 上实测为 400）**在这个聚合端点上不成立**——它替 DeepSeek 把这件事处理掉了。
2. **名字预测不了**：`qwen3-235b-a22b-thinking-2507` 名字里明写着 thinking 却 200，`qwen3.7-plus` 名字上看不出来却 400。
3. **两种拼法不能混用**：同一个端点上，`qwen3.8-max` 收 `enable_thinking:false`、拒 `thinking:{type:'disabled'}`；而 `api.deepseek.com` 上反过来。所以不能钉死一种，得试。
4. **字段发给不需要它的模型是无害的**——至少在这个端点上：两种写法发给 `gpt-6-sol` 与 `claude-sonnet-5` 都 200。这条是**反对**「按模型分别存」的证据，见下面为什么仍然按模型存。

## 一、字段存进配置，**按模型**存；预设只负责预填

今天 [`call.ts:121`](../../../src/agent/provider/call.ts) 在**发请求的那一刻**去 `PRESETS` 表里查字段：

```ts
const presetFields = PRESETS.find((p) => p.id === cfg.preset)?.request;
```

所以自定义端点（聚合商的地址就是这一类）永远查不到任何东西——这正是「一个端点用到底」这个用法下的根因。

改成：`ProviderConfig` 多一个按模型分的字段表，发请求时只读它，预设只在用户选中它时把值**预填**进去。

> **为什么按模型存，而不是一个端点一套。** 上面第 4 条说明一套也不会出事——在**这个**端点上。但字段本来就是某一个模型的属性（`qwen3.8-max` 要，`gpt-6-sol` 不要），而端点是会换的：OpenAI 原生对未知参数是直接报错的。按模型存还顺带买到一件用户能感觉到的事：**修好过的模型，下次挑回来仍然是好的**，不用再修一次。
>
> **为什么不是让用户自己填。** 那个 JSON 框仍然在（下面第四条），但它是给看得懂的人留的出口，不是流程的一部分。用户不知道 thinking 是什么，这一点是这张票存在的理由。

`PRESET_FIELDS` 那条一手文档纪律（架构守卫）原样保留：预设仍然声明自己那几个字段，守卫仍然要求每一条都有一手文档与实测。

## 一之后 · 实现时量到的一件事，把判据整个推翻了

**流式这条路上，这个端点把上游的原因吞掉了。** 同一个请求，只差一个 `stream` 开关：

```
stream=false  HTTP 400  "The tool_choice parameter does not support being set to required or object in thinking mode"
stream=true   HTTP 400  "openai_error"   type: bad_response_status_code
```

产品永远走流式。所以「端点原话里有没有 `thinking`」这条判据，**在真机上一次都不会命中**——拿产品自己的代码对着真端点跑才发现的，单测里永远撞不到。

判据因此改成两档，按钮都给：

- **`thinking`**——原话里真的有这个词（DeepSeek 原生端点、非流式代理会这样）。话说得肯定。
- **`refused`**——4xx，但端点没说为什么。话说的是「最常见的原因是……我替你试着关掉它再验一次」，不咬定。

> **为什么这样是对的，而不是退而求其次。** 这个出口本来就不靠「读懂报错」成立，靠的是「按一下就量出来了」。端点肯说，就说得肯定；端点不肯说，就说得有分寸，让那两次小调用去回答。真正不能做的是反过来——咬定一个没量过的原因。

**留给以后的**：要拿回那句真话，只能在失败之后用非流式再问一次，而这要协议层提供「同一个请求，不要流式」的说法（`prepare` 多一个参数）。这一票明说不改协议层，所以没做。

## 二、三种失败，三句不同的话

今天验收把所有失败都说成「这次验收调用没成功：<端点原话>」。实测里它们是三件完全不同的事：

| 端点的回答 | 这是什么 | 该说什么 | 三态开关 |
|---|---|---|---|
| 400，原话里有 `thinking` | 这个模型开着思考模式 | 肯定的人话 + **[关掉思考，再试一次]** | 不写（什么都没量出来） |
| 4xx，端点没说为什么 | 拒了，原因不明（聚合端点的常态） | 有分寸的人话 + **同一个按钮** | 不写 |
| 429 / 5xx，`上游负载已饱和` | **端点忙，不是配置问题** | 「这会儿端点忙，过一会儿再点一次验收就行」 | 不写 |
| 200，但没有调用工具 | 这个模型真的驱动不了本产品 | 「在这个端点上换一个模型」——**不是换端点**（一个端点用到底） | 写 `unsupported` |

判据是**端点自己的原话**，不是模型名——上面第 2 条说明名字不可靠。401/403 不在此列：Key 被拒跟这堵墙无关，不给按钮也不劝他关思考。

**同一个判断函数，两处用**：设置页验收失败时；以及引导跑到一半撞上同一堵墙时，那句「调用失败：…」后面也带上同一句人话，指向设置里的这个出口。不写两套判断。

## 三、那个按钮不猜，是量

两种写法互发都会 400（上表第 3 条），所以按钮做的事是**依次试**：

1. 先试 `{"enable_thinking": false}` → 通过就记在这个模型名下，告诉他「已经关掉思考（这个端点认的是这种写法），验收通过」
2. 还是 400 → 试 `{"thinking": {"type": "disabled"}}` → 同上
3. 两个都不通 → **一个字段都不写**，两次的原话都给他看

先试通义那种写法，因为撞墙的实测全部来自通义系。代价是最多两次几十 token 的调用，而且是用户点了才发生。

## 四、那个 JSON 框

设置页里露出**当前这个模型**的字段，可看可改，非法 JSON 当场拦下不发出去。它有三个用处：让用户看见产品到底替他加了什么、让看得懂的人自己加别的、以及把一个加错的字段删掉。

## 五、字段变了 = 没量过

`request` 加进「判决归属的那几样」：地址 / Key / 协议 / 模型 / **请求字段**。改任何一样，三态开关都退回「未知」——跟 01 那条同一个理由。

## Out of Scope

- **按模型名猜该发什么字段。** 上表第 2 条是直接反证：同一家的两个模型，名字里带 thinking 的那个好好的，名字上看不出来的那个撞墙。
- **别家别的必需字段。** 只认实测过的这一类；新的等真撞上了再加，不预先铺摊子。
- **替用户换模型**（比如撞墙时自动改成 `-nothinking` 那个孪生型号）。那是猜他想要什么。
- **能力矩阵界面 · 逐个探测 424 个模型**——与 01 同样的理由。
- **测评**。按 2026-09-25 的决定，这张票不带任何 eval 门槛；证据是类型检查、单测、e2e 与真机走一趟。
