# 05 — 运行循环：`violation` 走修复轮 + 「表里没有」诊断

**What to build:** 模型写了一个不在枚举里的动作名，扩展让它改一次就好了——而不是从此抱着一份已经被证明走不通的计划继续，把整轮引导拖死。

**`violation` 走修复轮。** 真机追踪统计得很干净：解析失败 3 次、修复 3 次，全救回来了；校验失败 2 次、修复 **0** 次。校验失败那一侧只标了「可重试」，而没有任何东西消费这个标记。两次校验失败（一个动作名不在枚举里、一个把两个 ref 拼成了一个字符串）**各报废一整轮**——因为被拒之后线程原封保留上一份计划，而那份计划已经被证明走不通。

两次都是模型自己改一个词就能对的错。修复机制现成，只是没接上。**恰好一次，绝不成环**，且仍然不含页面内容——沿用解析失败那条路的既有约定。

**「表里没有」诊断。** 模型在理由里表示「我需要的东西不在表里」时记一笔。真机出现过两次，我们一次都没接住。

**只诊断，不改变行为**：不给 `guide` 加「表里没有」的 schema 出口。如果 02 把裁剪修对了，那条出口就是死代码。这个事件的用途是**判断 02 是否真的修好了**——它是 06 号票唯一的运行时证据。

## 做完之后

**修复轮从「按失败种类各来一次」改成「按抽次来一次」。** 解析和校验现在是同一个判决（`verdictOf`），所以一次抽签最多买一次修复——一份先解析通过、再被校验拒掉的输出，已经把那次机会用掉了。

**诊断探针拿真机数据校准过，不是拍脑袋定的关键词。** 86 条真机 `why` 上：只匹配「元素表/表里/表中」会命中 13 条，其中 **4 条是误报**——「建议列表中选择」「结果列表里第一个正是目标仓库」这类，说的是模型成功读到了表。要求「表的提及」附近有否定词之后，命中 12 条、误报 0 条，还多捞出 3 条第一版漏掉的真阳性。

**基线：12/86 ≈ 14% 的规划理由在说「我要的东西看不见」。** 这就是 06 号票要压到零的数。

分母口径要写死，否则对不上：**从 `ok` 的计划里取 `steps[].why` 与信封自己的 `why`**，共 86 条（去重后仍 86）。评审用另一种口径数出 99 条、命中同样是 12。比较时必须用同一个口径。

> 票头补记（2026-09-26）：两半都在。`violation` 与解析失败合成一个判据、共用那一次修复轮（`runner.ts` 的 `verdictOf`）；「表里没有」记成 `not_in_table` 事件（`trace.ts` / `shared/types.ts`）。
