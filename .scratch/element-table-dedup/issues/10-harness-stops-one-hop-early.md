# 10 — 尺子提前收工，把 5 轮健康的引导记成了失败

**What to build:** 真机脚本走完产品愿意走的每一步，而不是在「这一跳没产生新的模型调用」时就收工。

## 证据

21 轮里有 5 轮（P1-1 / P1-4 / P2-1 / P3-3 / P3-5）停下时，线程里**还挂着一个没走的 `input「Search or jump to」`**——正是把 `n8n-io/n8n` 敲进去、推动旅程的那一步。

```
第1跳  点「Open quick search dialog」→ 搜索框弹出，URL 不变
       重规划触发 ✓ → 新计划 [点搜索框, 输入 n8n-io/n8n]
第2跳  点「Search or jump to」（新计划第 1 步，click）
       → 页面不变（框本来就开着）→ 重规划判 page-unchanged → 不发模型调用
       → 产品正确地把 cursor 推到第 2 步 = input
       → harness 见「没有新的模型调用」→ break
第3跳  从未发生
```

`live-github-run.mjs` 的 `if (!after) break`，注释假设「断点没触发 = 没有新东西可走」。**该假设对单步计划成立，对多步计划是错的**：多步计划里一步不改变页面本来就不该重规划，产品靠 `handleStepSettleTimeout` 推进游标，那时**有**新东西可走。

harness 本身会输入（步骤标 `input` 时它点中、全选、打字、回车）——它只是没走到那一步。

## 做完之后

**break 判据**从 `if (!after) break`（没有新的模型调用就收工）改成看线程是否推进：

```js
const advanced = final !== null && (final.callCount !== callsBefore || final.cursor !== cursorBefore);
if (!advanced) break;
```

**刻意不看 `rev`**：归约器对被拒的输入也会 `rev + 1`，拿它当判据会让一个死步骤空转到跳数上限。两个信号各有明确含义——新调用 = 有新计划，游标动了 = 现有计划还有下一步。

**拿上一轮日志核对过**：那 5 轮（P1-1 / P1-4 / P2-1 / P3-3 / P3-5）收尾时 cursor 都从 0 推到了 1，新判据下会继续走；而真正冻住的三轮（P1-5 / P1-7 / P3-1）cursor 始终是 0、调用数也没变，新判据下照旧收工，不会空转。

**跳数 6 → 8。** 但顺序很重要：09 先做。只放宽预算而不减少走错，等于给错误更多绕圈的空间。

## 顺带修掉一个咬过两次的耦合

golden 重录时测试 30 连着两次报红，原因是 spike 的 `TABLE_ZH_CONSOLE` 直接读 `tests/eval/captured/zh-console.json`，而 eval 抓取服务器用 `listen(0)` 随机端口——**任何一次 `npm run eval` 都会让它和语料里存的那张表对不上**。

第一次是手工同步的，这次改成**让生成器每次连那张表一起重建**，从此不会再漂。
