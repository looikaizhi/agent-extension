## 失败归因（2026-09-07 与用户逐条过完）

21 轮里 3 轮确认到达。剩下的失败按根因分四类，**其中两类不在产品里**。

### ① 测量提前收工 —— 5 轮（P1-1 / P1-4 / P2-1 / P3-3 / P3-5）

这五轮停下时，线程里**还挂着一个没走的 `input「Search or jump to」`**——正是把 `n8n-io/n8n` 敲进去、推动旅程的那一步。

harness **会**输入（步骤标 `input` 时它点中、全选、打字、回车）。问题是它在轮到那一步之前就退出了循环：

```
第1跳  点「Open quick search dialog」→ 搜索框弹出，URL 不变
       重规划触发 ✓ → 新计划 [点搜索框, 输入 n8n-io/n8n]
第2跳  点「Search or jump to」（新计划第 1 步，click）
       → 页面不变（框本来就开着）→ 重规划判 page-unchanged → 不发模型调用
       → 产品正确地把 cursor 推到第 2 步 = input
       → harness 见「没有新的模型调用」→ break
第3跳  从未发生
```

罪在 `live-github-run.mjs` 的 `if (!after) break`，注释假设「断点没触发 = 没有新东西可走」。**该假设对单步计划成立，对多步计划是错的**：多步计划里一步不改变页面本来就不该重规划，产品靠 `handleStepSettleTimeout` 推进游标，那时**有**新东西可走。

**产品的最后一个动作是「准备好让用户输入」，而尺子在那一刻收了工。**

### ② 跳数预算用完 —— 4 轮，其中 3 轮差一跳

一跳 = 一次用户点击，上限写死 6（`live-github-run.mjs:582`）。**这是测试脚本的限制，产品自己没有跳数上限。**

不是重复执行，也不是一跳变两跳——是走错一步之后要花 2–3 跳绕回来。P3-7 实际点击序列：

```
1 Open quick search dialog   ← 必要
2 Search or jump to          ← 必要
3 n8n-io/n8n                 ← 必要，已进仓库
4 Security and quality (180) ← 走错 ✗
5 n8n-io                     ← 往回退 ✗
6 n8n                        ← 退回仓库，等于回到第 3 跳 ✗
  还剩「Actions」            ← 第 7 跳，预算没了
```

P2-7 同型（停在「workflows, (Directory)」差一跳）、P2-4 同型（第 3 跳点了 Issues，花 3 跳绕回）。**三轮都是「错一步，赔三跳」。**

### ③ schema 把决定放在理由前面 —— ②的根因，用户认同

反复出现的形状，P3-7 第 3 跳的 `why`：

> 选「Security and quality (180)」会进入该仓库的安全与质量相关页面；**不过更贴合 CI 配置的是进入 Actions 或 .github 目录**

**模型在同一句话里说出正确答案，`ref` 却指向错的那个。** P3-4 更明显——理由写到一半自我否定「但这里我用的是 Tags 链接——不对……」，然后还是点了 Tags。

字段顺序：

```
我们：       required: ['ref', 'action', 'value', 'why', 'expect_after']
                        ↑决定                      ↑理由
browser-use：['evaluation_previous_goal', 'memory', 'next_goal', 'action']
              ←──────── 三个反思字段 ────────→        ↑动作
```

自回归是逐字段往下写的——**我们让模型先承诺一个 ref，再为它编理由**。研究报告 §3.1 记着 browser-use 是**手工覆写** `required` 把反思顶到动作前面的，那是刻意为之。

**②和③是同一件事的两面：③让它走错一步，②让它没有余地绕回来。**

### ④ 「官方文档站」3/3 停在澄清 —— 用户判定这是**正确行为**

三遍全部 0 跳停在 CL-1，理由都是「官方文档站有歧义：GitHub 仓库里的文档，还是 docs.n8n.io？」

我原本把它算作违反 `TOOL_CHOICE_POLICY` 那句「『这一页上没有直接通向目标的链接』不是理由」。**用户不同意，并且用户是对的**：从 github.com 确实进不去 n8n 的官方文档站，那是另一个站点。模型停下来问，是诚实的。

用户的处理方向：**以后做一个专门的工具**——让 agent 判断当前站点能不能到达目标，不能就用这个工具让用户确认是否跳转到 agent 给出的站外页面。**现在不做。**

所以这一类不是缺陷，是**能力缺口**：产品目前没有「目标不在本站」这个出口，模型只能退而求其次用 clarify。
