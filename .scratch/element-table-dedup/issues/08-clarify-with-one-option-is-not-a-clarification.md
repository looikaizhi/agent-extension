# 08 — clarify 的选项形状：一个不算澄清，而「以上都不是」现在表达不了

**What to build:** 用户说「把这台实例删掉」，页面上就一个「删除实例」按钮，扩展直接把它指出来——而不是反问一句「你要点下面这个按钮吗？」然后只列出那一个按钮。

## 证据

2026-09-06 重录 golden 语料时抽到的一条（slice 1，目标 `把这台实例删掉`）：

```json
{
  "question": "这个页面上有\"删除实例\"按钮（e8），但删除实例是一个不可逆且涉及公网IP、快照、安全组等高影响的危险操作。在动手之前我需要你确认。你可以参考下面哪个按钮继续？",
  "options": [{ "ref": "e8", "label": "点击\"删除实例\"按钮，继续删除这台实例" }]
}
```

模型**找到了入口并点了名**，然后把它包成一个单选项的问题。`TOOL_CHOICE_POLICY` 给 clarify 的两个条件——「目标本身有歧义（这一页上有多个同样合理的对象）」和「连一个能让用户更接近目标的入口都没有」——**一个都不成立**。

「只有一个选项的澄清」在定义上自相矛盾：它没有在澄清任何东西，它在要求确认。而确认是另一件事，产品里已经有专门的机制（跨站确认）。策略里那句「列出全部候选，不要替用户选一个」也预设了候选不止一个。

## 为什么现在值得做

05 号票刚把校验失败接上了修复轮。加上这条规则之后，这类输出会被判 violation → 修复轮告诉模型哪里不对 → 它大概率改成 `guide`。**机制现成，只差一条判据。**

## 采样说清楚

**n=1，不要当成回归定论。** 同一次重录里，采样最足的 slice 4（五次抽样，页面上有两个一模一样的「删除」按钮）从 3/5 clarify 变成 5/5 clarify，那是**正确**方向——真有歧义时就该问。变的只有 slice 1 这一条单抽。

语料头注释自己记着这个教训：一次 temperature 1 的抽样分不出 20% 和 60% 的差别。所以这张票的理由**不是「模型退步了」**，而是「单选项 clarify 这个形状本身就不合法，无论它多久出现一次」。

## 同一次重录还暴露了相反方向的一个缺口

第三次重录抽到 slice 3（`把这台实例的语音助手功能关掉`，页面上确实没有这个功能）：

```json
"options": [
  { "ref": "e9", "label": "我不确定,让我看看开发者文档里有没有说明" },
  { "ref": null, "label": "其实我说的就是安全组/网络相关的某种设置(请说明)" }
]
```

第二个选项**没有 ref**——它是「以上都不是，我再说清楚点」。这不是乱写：`docs/research-dom-serialization-and-arrival.md` 记过 Mind2Web 的多选形状**每一组都带一个 `A. None of the above`**，而我们的 schema 把 `options[].ref` 声明成必填字符串，模型只能写 `null`。

所以 clarify 的选项形状有两个方向的问题，该一起定：

- **下界**：一个选项不算澄清（上面那条）
- **上界**：真正的「以上都不是」现在表达不了，模型只好塞 `null` 进去，然后整封信被拒

这一条**没有先例可抄**（四家一手来源里只有 Mind2Web 有，而它是多选题不是工具调用），所以要不要开这个口子是产品判断，不是照抄。**注意它和 R-a/R-e 的关系**：没有 ref 的选项没有可核对的东西，`claimedRefs` 得跳过它，那正是安全规则赖以生效的地方——开口子之前要想清楚这一点。

## 核对（2026-09-27，对着当前代码与真跑数据）

**后半张「以上都不是」已经过期。** 这张票写于 2026-09-06，那时答案只能从选项里挑。对话面板（2026-09-20/21）之后：

- 选项在侧栏里只是一个 `<li>` 列表，代码注释写着「none picked for the user (K-6): the answer is theirs to type」；
- 输入框**从不禁用**，占位符是「引导在走，你也可以直接说」。

用户打一句「都不是」就会作为 `said` 读数回到那趟等着的引导。所以这一半不用做了。

**前半张还在，但很小。** `ask.ts` 的 `violation` 至今只拦「`wants=choice` 却零个选项」，一个选项照样放行。不过量级要说清楚：

| | ask/clarify 的选项个数 |
|---|---|
| t09（358 次调用） | 2 / 3 / 3 / 3 —— **没有一次是单选项** |
| t11（243 次调用） | 1 / 4 —— **一次** |
| batch-2/3（新词表） | 一次 ask 都没有 |

601 次调用里撞到 1 次。而且这张票的证据来自 `clarify` 时代——之后工具描述改写（把「先问用户」换成一条带门槛的说明）把反问率从 16% 压到约 1%，那次改写顺手削掉了这个缺陷的大部分发生面。

**要做的话**：把判据从 `length === 0` 改成 `length < 2`，让它走修复轮。一行。但按当前的数据，它排在任何别的事后面。

## 做完了（2026-09-27）

**只改了校验，没碰提示词。** `ask.ts` 的判据从「零个选项」放宽到「少于两个」，违例的话直接说该改用 `point`——那句话会在修复轮里递给模型，效果和改提示词一样，而改提示词会让 `prompt.spec.ts` 第 29 条（逐字比对一次真实请求的 system 消息）变红，代价不对等。

新增三条单测：一个选项被拦且话里点名 `point`、两个候选照旧放行、`wants=text` 不受这条管。顺带补了两处**夹具**——`one-step.spec.ts` 与 `offered-values.spec.ts` 里的 ask 夹具碰巧只列一个候选，它们测的是 wants/intent 认不认，不是选项个数。
