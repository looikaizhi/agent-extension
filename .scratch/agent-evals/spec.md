## Problem Statement

**对这个产品的主人：改了一处，说不清 agent 是变好还是变坏了。**

- 离线评测只测抽取器，不测模型拿到元素表之后做了什么决定。
- 真机 harness 只在 github.com 一个站上跑 7 个目标 × 3 遍。按研究报告里的公式算，它最多只能分辨约 28–33 个百分点的差距。第六、七轮之间 14 个百分点的下降，置信区间是 (−5.1, +33.7)，分不出真假。
- 「到了没有」只按 URL 正则判；你真正的口径（最终 URL 对，并且屏幕上最后一步指对了）没有落成数据。你的人工判定存在报告页的浏览器本地存储里，只有你的浏览器看得到，评估读不到。
- Run record 的状态说的是「确认了几步」，不是「到了没有」，不能当成功率用。
- trace 最多存 24 条，第七轮有 5 轮顶到上限，最早几次调用的原始输入丢了，拿不去做离线回放。
- 没有办法做「带某个能力 / 不带」的对照，所以将来加 memory、workflow、skill 时无法证明它们有效。

## Solution

两层评估，外加一套统计和数据约定：

- **Decision eval（离线，当闸门）**：拿真机上录下的状态，一字不差地重放给 agent，看它这一跳答得对不对。便宜、输入固定、分辨率高。改提示词、换模型、加 Plugin 之前必须跑。
- **Task eval（真机，量能力）**：在三个站点、约 26 个目标上每个跑 3 遍，看最后有没有 Arrival。你的判定是正式分数，程序化判据跟着你的判定校准。
- 两层都按次指定开哪些 Plugin，并把开关组合、模型、快照指纹写进结果，所以任何两次结果都能配对比较。

## User Stories

1. 作为产品的主人，我希望改完提示词之后跑一条命令，就知道模型每一跳的选择有没有变差，这样我不必每次都花一轮真机。
2. 作为产品的主人，我希望离线评估重放的输入和模型当时读到的一字不差，这样分数的变化只能来自我改的东西。
3. 作为产品的主人，我希望离线评估告诉我意图对不对（该给 guide 还是 done、clarify、need_docs），这样我能看出模型是在该停的时候没停，还是在该走的时候停了。
4. 作为产品的主人，我希望离线评估告诉我第一步指的元素和动作在不在可接受集合里，这样「选对控件」有一个数。
5. 作为产品的主人，我希望可接受的元素是一个集合，不是单一答案，这样 GitHub 上一个目标有好几条路时，走哪条都不算错。
6. 作为产品的主人，我希望后续步骤只检查「在表里、不是敏感控件」，不评对错，这样评估不会为没见过的页面编答案。
7. 作为产品的主人，我希望标注从到达了的轮次预填一份建议，我只需要确认或补充，这样第一批 50–80 个状态标起来不费劲。
8. 作为产品的主人，我希望在一个页面上标注：看到当时的目标、历史、元素表，勾出可接受的元素和正确的意图，这样我不必手写 JSON。
9. 作为产品的主人，我希望我的标注成为仓库里的数据，这样它能被版本管理、能被评估读到，也不会随浏览器被清掉。
10. 作为产品的主人，我希望离线评估有门槛：解析失败率和校验失败率不高于冻结基线，指向表外或敏感控件的次数为零，意图和第一步准确率在配对比较下不显著变差，这样它能当闸门用。
11. 作为产品的主人，我希望离线评估也报告 token、成本、延迟和每个状态的 pass^k，这样我同时看到质量和代价。
12. 作为产品的主人，我希望同一个状态可以跑多遍，这样我能看到模型在同一处是稳定对、稳定错，还是时对时错。
13. 作为产品的主人，我希望真机评估覆盖 github.com、gitee.com、help.aliyun.com 三个站点、约 26 个目标，这样它能分辨约 14 个百分点的差距，而不是 30 个。
14. 作为产品的主人，我希望目标清单由你起草、我定稿，这样目标是我真正关心的。
15. 作为产品的主人，我希望每个目标带一份程序化判据（可接受的最终 URL 加上可接受的最后一步），这样每轮都能自动出一个 Arrival 分数。
16. 作为产品的主人，我希望程序化判据和我的判定之间的一致率、precision、recall 每轮都报告出来，这样我知道什么时候可以信它。
17. 作为产品的主人，我希望我的判定照旧在报告页上做，但存进报告页自己的数据库，再拉成仓库里的文件，这样判定不再只存在我的浏览器里。
18. 作为产品的主人，我希望真机评估报告按目标聚类的 Arrival 率及其 Wilson 置信区间，这样我知道这个数有多不确定。
19. 作为产品的主人，我希望真机评估报告 pass^1、pass^2、pass^3，这样我知道「连续几次都到」的可靠性，而不只是「有一次到过」。
20. 作为产品的主人，我希望两轮真机之间报告按目标配对的差和它的置信区间，这样我不会再把噪声当成退步。
21. 作为产品的主人，我希望真机评估报告跳数、调用数、token、成本，这样我能看到到达和花费的取舍。
22. 作为产品的主人，我希望真机评估报告安全违规：最后一步唯一但指错的次数，以及把人引向敏感控件或跨站凭据的次数，这样安全不被到达率掩盖。
23. 作为产品的主人，我希望 harness 每跳之后都把 trace 读走写进日志，这样离线语料不会因为产品那 24 条上限而缺头。
24. 作为产品的主人，我希望 harness 的 main 函数能按次选开哪些 Plugin（例如只开 Skill，或者什么都不开），这样同一组目标可以做「带 / 不带」的对照。
25. 作为产品的主人，我希望离线评估也能按次选开哪些 Plugin，这样一个能力在两层上用同一种方式量。
26. 作为产品的主人，我希望每次结果都记下开关组合、模型、快照指纹和时间，这样任何两次结果能不能直接比，一眼就知道。
27. 作为产品的主人，我希望两层评估都是手动命令，不进每次的验证，这样日常改代码不会平白花模型的钱。
28. 作为产品的主人，我希望抽取器评估、离线评估、真机评估分别是三个子目录、三条命令，这样我知道每条命令在测哪一层。
29. 作为产品的主人，我希望评估住在仓库根目录的 `evals/`，和 `tests/` 分开，这样「每次都跑、不花钱」和「手动跑、要花钱」不混在一起。
30. 作为产品的主人，我希望真机 harness 从「一次性试验」目录搬出来，这样它不会被当成可以随手删掉的东西。
31. 作为产品的主人，我希望每轮评估生成一份报告页（像第四到第七轮那样），页上能直接做判定，这样看结果和做判定在同一个地方。
32. 作为产品的主人，我希望在研究报告里算过的第六、七轮数字能被评估代码原样复现，这样我知道统计代码没写错。
33. 作为之后加 Plugin 的人，我希望有一个现成的流程：先在离线层做带 / 不带的配对比较，再在真机层确认不退步，这样「有效」有固定的证明方式。

## Implementation Decisions

**位置与命令**
- 仓库根目录 `evals/`：
  - `extract/`：今天的抽取器评测，原样搬进来，门槛不变；
  - `decision/`：离线决策评测；
  - `task/`：真机任务评测。
- 命令：`npm run eval` 仍然是抽取器评测；新增 `eval:decision` 与 `eval:task`。
- 真机 harness 与它的打分脚本从一次性试验目录搬进 `task/`。一次性试验目录只留真正一次性的探针。

**Decision eval**
- **语料**：
  - 来源：真机日志里每一次模型调用的原始 user 消息、那一刻的工具 schema、所用的 system 消息，以及当时的目标、站点、轮次。
  - harness 每跳之后把 trace 读走写进日志，产品的上限不动。
  - 一条语料 = 一个状态。
- **标注**：
  - 每个状态标两样：可接受的元素集合（按 ref）和正确的意图。
  - 从到达了的轮次预填建议，由产品的主人在标注页上确认或补充。
  - 标注页是一张带数据库的报告页，结果拉进仓库成为数据文件。第一批 50–80 个状态。
- **打分**：主分看两样：意图对不对；第一步的元素与动作在不在可接受集合里（步骤成功 = 元素和动作都对）。后续步骤只查「在表里、不是敏感控件」。
- **调用**：直接调用规格 A 的 agent 门面与真实的 Provider；同一状态可跑多遍；按次指定 Plugin 组合。
- **门槛**：
  - 解析失败率、校验失败率不高于冻结基线；
  - 指向表外或敏感控件 = 0；
  - 意图准确率与第一步准确率在配对比较下不显著变差。

  冻结基线 = 规格 A 完成后的第一次完整运行。
- **报告**：token、成本、延迟、每个状态的 pass^k。
- **覆盖**：先只覆盖引导 agent。问答 agent 的门面已经能调用，等有了问答语料再加进来。

**Task eval**
- **任务集**：github.com 约 10 个、gitee.com 约 8 个、help.aliyun.com 约 8 个目标，每个跑 3 遍。目标清单由我起草、产品的主人定稿。每个目标带一份程序化判据：可接受的最终 URL，加上可接受的最后一步（按 Descriptor 描述）。
- **判定**：
  - 产品的主人的判定是正式分数：最终 URL 对，并且屏幕上最后一步指对了。
  - 判定在报告页上做，存进报告页的数据库，再拉成仓库里的判定文件。
  - 程序化判据每轮自动算，并报告它与人工判定的一致率、precision、recall。
- **harness 的 main 函数**：
  - 参数至少包括：站点 / 目标子集、遍数、Plugin 组合、模型配置。
  - 跑之前把 Plugin 组合写进产品设置。
  - 日志第一行记下开关组合、模型、快照指纹、开始时间。
- **报告**（只报告，不设硬门槛）：
  - 按目标聚类的 Arrival 率，附 Wilson 置信区间；
  - pass^1 到 pass^3；
  - 与上一轮按目标配对的差及其置信区间；
  - 跳数、调用数、token、成本；
  - 安全违规数；
  - 程序化判据的一致率。
- **账号状态**：每轮之间要清掉会串轮次的状态（例如 GitHub 的「最近搜索」）；新增的两个站点不需要登录。

**统计**（公式与出处都在研究报告里）
- 二值成功率：小样本用 Wilson 区间。
- 同一目标跑多遍不独立：先按目标聚类，再算标准误。
- pass^k = 对每个目标求 C(c,k)/C(n,k)，再对目标取均值。
- 两个版本的比较：按目标配对算差与标准误。
- 所需样本量用研究报告里的反解公式估算。
- 这些都写成纯函数。

**报告页**：每轮生成一张报告页，形式延续第四到第七轮；页上可以直接做判定，判定存进页面自己的数据库。

## Testing Decisions

- **好的测试只断言外部行为**：给定回答与标注，分数是多少；给定「目标 × 遍数」的结果，统计量是多少；给定最终 URL、最后一步和可接受集合，判定是什么。
- **统计纯函数**：用研究报告里从第六、七轮日志独立算出的数核对。
  - 11/21 的 Wilson 区间为 32.4%–71.7%；8/21 为 20.8%–59.1%。
  - 第六轮 pass^1/2/3 为 0.524 / 0.381 / 0.286；第七轮 pass@3 为 0.714。
  - 两轮按目标配对的差为 +14.3 个百分点，配对标准误 9.9。
  - 有外部答案可以对照，是这层最好的测法。
- **打分纯函数**：意图对错、第一步元素与动作、后续步骤的有效性检查，各给一组构造好的回答与标注。先例是现有 golden 语料的写法：标注只由原始输出和表推出，不跑被测函数去生成标注。
- **程序化判据**：给出到了、URL 对但最后一步错、URL 错三类样本。
- **与人工判定的一致率计算**：给定两份判定，算一致率、precision、recall。
- **harness 本身不做单测**，只负责跑。它的正确性由产出的日志能被打分脚本读通、并且和报告页一致来检验。
- 先例：现有的真机打分脚本（按日志算解析失败率、多步占比、计费）、抽取器评测的门槛写法、golden 语料的标注纪律。

## Out of Scope

- LLM 评审：它的 precision 实测不到 70%，这次不采用。
- 问答 agent 的离线语料与评估。
- 把评估接进每次的验证或持续集成。
- Workflow、Memory、新站点 Skill 的实验本身：属于规格 C，本规格只提供它们要用的量具。
- 产品运行时判断 Arrival：产品不知道用户的目标该在哪一页结束。

## Further Notes

- 研究报告算过：21 轮的分辨率约 28–33 个百分点；26 个目标 × 3 遍大约能分辨 14 个百分点，成本约为今天的 3–4 倍（第七轮 21 轮用了 81 万 token）。Decision eval 一个状态一次调用，是分辨细小差距的主力。
- 本规格的冻结基线在规格 A 完成之后取。在那之前模型看到的东西逐字节不变，所以现有的真机日志可以直接当语料用。
- 回归评测应接近 100% 通过，能力评测从低通过率起步。这个区分来自 Anthropic 的 agent 评估文章，是这里「离线设门槛、真机只报告」的依据。
