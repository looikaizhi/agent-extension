# 04 — harness 记下每一次模型调用的完整输入

**What to build:**

Decision eval 的语料来自真机日志，但今天的日志不够用：

- 完整的调用参数只在开局那一跳存了；之后每一跳，元素表只剩网址、标题和条目数。
- trace 里有 user 消息原文，可产品只留最近 24 条。第七轮 21 趟里有 5 趟顶到上限，最早几次调用的原文丢了。
- trace 存了 system 消息，没存工具 schema。

改成：

- **每一跳之后把 trace 读走**，只追加比上次读到的更新的条目。产品那 24 条的上限不动。
- **每次模型调用的请求参数原样存下**：目标、整份元素表、历史、Plugin 的贡献、新出现的 ref。每一次都和 trace 里对应的那次请求配成一对。
- **trace 像存 system 消息那样存一份工具 schema**。运行循环的请求事件本来就带着它，只是 trace 没存。这只改调试记录，发给模型的东西不变。
- **日志里一次模型调用只有一种记法**：今天开局一种、后续每跳一种，打分脚本的 `callsOf` 为此写了两套读法。合成一种，两套读法一起删。旧日志从此不能用新脚本打分；它们的数已经写在当时的报告页上。

**实现记录**
- **与票面的出入：trace 从消息流里取，不每跳去读宿主存的那份**。
  - 侧栏回传每次调用结果的 `EFFECT_RESULT`，本来就带着这一次调用的 trace（调试开关打开时）。harness 按 `effectId` 把它和请求配成一对。
  - 宿主存的那份有 24 条上限的 trace，harness 不再读。票面要的是「不因上限丢头」，这样做同样满足，而且配对是天然一对一，不必按时间去切。
- **消息流整趟只在开局清一次**：原来每一跳开始时都清一次，两跳之间发出的调用（例如分两段加载的页面第二次重新规划）会丢。现在每一跳记下自己在消息流里的起点，按位置切出自己那一段。
- **日志里一次模型调用只有一种记法**：每次调用一行 `kind: 'call'`。
  - 字段：第几遍、目标 id、这一趟的第几次调用、`hop`（请求在哪一跳的窗口里发出，0 是开局）、`effectId`、`params`（原样，含整份元素表）、`outcome`（原样）、`trace`（这一次的 system、工具 schema、条目）。
  - 跳里的 `plans`、`sent`、`usage` 删掉，换成 `effects`：这一跳发出的调用的 `effectId`。趟那一行不再带 trace，开局那一行不再带整段消息流。
- **产品改动只在调试记录**：`Trace` 加 `tools` 字段。`createTrace` 从请求事件里存一份，和 system 一样只存一次；`mergeTrace` 取这一次的。trace 不发给模型，快照逐字节不变。
- **工具 schema 按同一个上下文核对**：它由 `outputSchema(ctx)` 按上下文生成，所以正确的比法是：每次调用的 trace 与用这次调用自己的参数算出的 schema 比较。指纹函数用的是同一个函数，只是换成它自己的固定输入。
- **`score-run.mjs` 整个重写**：
  - 只读 `kind: 'call'` 行，原来开局、后续两套读法都删了；
  - 没等到结果的调用单独计为 `unanswered`，不进任何比率。以前这种调用会被算成解析失败；
  - 键名 `rounds` 改为 `trips`，`hops_per_round` 改为 `hops_per_trip`；到达率标明「URL」；
  - 旧日志从此不能用它打分，它们的数已经写在当时的报告页上。
- **删掉的死代码**：`probeBreakpoint`、`reportProbe`（没有调用者）、`modelCalls`、`traceOf`，以及只为 `probeBreakpoint` 服务的 `pageMoved` 动态 import。
