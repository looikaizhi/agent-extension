# 11 — 离线语料：从真机日志抽出状态，并证明能逐字节重放

**What to build:**

一个状态 = 一次模型调用。从第 04 张之后的真机日志里抽，存进 `evals/decision/`，进版本管理。

- **每个状态存三样**：
  - 结构化的 Context：目标、元素表、历史、新出现的 ref、页面 URL、当时的 Plugin 组合与各 Plugin 贡献的原文；
  - 模型当时读到的原文：system 消息、工具 schema、user 消息；
  - 来历：轮次、目标、站点、第几遍、第几跳、快照指纹，以及模型当时的回答原文（第 12 张预填要用）。
- **为什么还要存结构化的 Context，不只存原文**：Decision eval 要按次开关 Plugin，而站点技能在 user 消息里，只有原文就换不掉它。原文的用处是证明重放没走样。
- **逐字节核对**：
  - 用当前代码、按状态自己的 Plugin 组合重新拼出消息，与存下的原文比较，包裹标记换成固定值；
  - 快照指纹与状态相同时，必须完全一致。不一致的状态不收，并报出是哪一段不一样。
- **换一组 Plugin 时**，贡献用产品自己的收集函数按页面 URL 重算，评估里不另写一份。
- **旧日志不当语料**：它们只在开局那一跳存了完整参数，而且是 Plugin 之前的形状（`siteNotes`）；之后每一跳，元素表只剩条目数。规格原先说现有日志可以直接当语料，这一点做不到。第一批语料来自第 09 张那一轮。

**实现记录**
- **位置**：`evals/decision/corpus.ts`（抽取、重拼、核对），`evals/decision/extract.mjs`（命令行）；测试在 `tests/unit/decision-corpus.spec.ts`。
- **一个状态存三样**：
  - 结构化的 Context：目标、整份元素表、历史、新出现的 ref，以及这一轮的 Plugin 组合和这次调用得到的 Plugin 贡献原文；
  - 模型当时读到的原文：system、工具 schema、user 消息，取自这次调用自己的 trace；
  - 来历与回答：轮次、目标 id、第几遍、第几跳、第几次调用、快照指纹，以及面板回传的回答（`EffectOutcome`，第 12 张预填要用）。
- **一次调用一个状态**：状态取这次调用的请求，修复轮属于它修的那次调用，不单独成状态。没有 trace 的调用（没等到结果，或调试开关没开）跳过，并写明原因。
- **逐字节核对**（`differences`）：用当前代码、按状态自己的 Plugin 组合重拼，再和原文比，分四段报：Plugin 贡献、system、工具 schema、user 消息。
  - Plugin 贡献按宿主的收法重算：用产品自己的收集函数，按这次调用元素表的网址（`thread/writer.ts` 就是这样收的），不照抄记录；
  - 包裹元素表的随机标记，两边都换成同一个固定值再比。
- **命令行**：`extract.mjs <轮次 id> [--out 文件]`。逐个核对，有一个对不上就以非零退出；给了 `--out` 才写，每行一个状态，对不上的一律不写。这一轮的快照指纹和当前代码不同时，会提示「发给模型的东西已经变了，要用产生这一轮的那一版代码来抽」，但照样逐个核对。
- **旧日志不能当语料**：它们没有第一行（第 03 张之前的日志），抽取时直接报错。
- **与票面的出入：本票没有往仓库里写语料**。一个状态带整份元素表，大约 40KB；第 09 张那一轮约 78 趟、四五百次调用，全部写进仓库会有十几 MB。所以仓库里只放第 12 张挑出的那一批（`--out` 写进 `evals/decision/`），不放每一轮的全部状态。
