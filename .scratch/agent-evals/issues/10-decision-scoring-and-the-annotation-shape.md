# 10 — 离线打分的纯函数，与标注的格式

**What to build:**

Decision eval 看模型在一跳上答得对不对。这张票只写打分，不调模型。

- **一条标注**：状态 id；正确的意图（guide、done、clarify、need_docs）；意图是 guide 时，第一步的可接受集合，每一项是一个 ref 和它可接受的动作。GitHub 上一个目标常有好几条路，所以是集合，不是单一答案。
- **给一个状态的元素表、模型的回答和标注，打出**：
  - 意图对不对。引导调用收到问答的信封（例如 explain）算意图错，不算解析失败（decisions.md「引导调用收到问答的信封」）；
  - 第一步：元素在可接受集合里、动作也在，才算步骤成功。元素与动作分开报；
  - 后续步骤：只查 ref 在这张表里、不是 Sensitive 控件，不评对错；
  - 解析失败、校验失败（运行循环交回的失败种类）单独计数，不混进意图错。
- **「在表里、不是敏感控件」直接对着状态里存的元素表判，不调用产品的 R-a/R-e**：产品的校验要是错了，评估不能跟着一起错。读回答仍用产品自己的解析器，理由与 `score-run.mjs` 相同：宽容的解析是产品真实的行为。
- **汇总**：每个状态跑 k 遍，一个状态是一个簇。用第 02 张的函数给出意图准确率、第一步准确率及其区间，以及每个状态的 pass^k。

**Blocked by:** 02 — 统计的纯函数，先复现第六、七轮的数

**实现记录**
- **位置**：`evals/decision/score.ts`；测试在 `tests/unit/decision-score.spec.ts`。
- **一条标注**：`{ state, intent, acceptable? }`。`intent` 是 guide、done、clarify、need_docs 之一；意图是 guide 时，`acceptable` 是可接受的第一步集合，每一项是一个 `ref` 和它可接受的动作列表。
- **打分的输入**：运行循环结果（`RunResult`）里打分要用的部分——原文、工具名、失败种类。第 13 张直接把运行循环的结果交给它。
- **一次回答的四种结局**：
  - 网络错：模型什么都没说，不算对也不算错，汇总时不进任何分母；
  - 解析失败：修复后仍读不出，意图算错；
  - 被校验拒掉：算失败，但照样从原文里数它指向了哪些表外或敏感控件，因为闸门看的就是这个数；
  - 答了：问答的信封（例如 explain）算意图错，不算解析失败。
- **第一步，元素和动作分开判**：元素看它在不在可接受集合里。动作在元素对时，看这个元素自己的可接受动作；元素错时，看整个集合里出现过的动作，所以「点对了类型、点错了控件」判得出来。两者都对，才算步骤成功。
- **「在表里、不是敏感控件」直接对着状态自己的元素表判，不调用产品的 R-a/R-e**：回答指向的每一个 ref（所有步骤、clarify 的每个候选、need_docs 的 `via_ref`）都要查。读回答仍用产品自己的解析器。
- **标注本身不合法就直接报错**：可接受的 ref 不在表里、是敏感控件，或意图是 guide 却没给集合。
- **汇总**（`summarize`）：一个状态是一个簇，用第 02 张的函数给出：
  - 意图准确率、第一步准确率（只算该给 guide 的状态），附聚类 Wilson 区间；
  - 每个状态的 pass^1 到 pass^k；
  - 稳定对、稳定错、时对时错各有几个状态；
  - 解析失败率、校验失败率（分母是到达了模型的回答），以及指向表外、指向敏感控件的回答各有几次。

**变异探针**（10 个全红；还原后哈希一致）
- D1 不查表外 ref → 后续步骤、被拒的回答两条红
- D2 不查敏感控件 → 敏感步骤、clarify 候选两条红
- D3 只查第一步、不查后续步骤 → 后续步骤两条红
- D4 问答的信封当成解析失败 → explain 那条红
- D5 元素错时动作一律判错 → 「元素错、动作对」那条红
- D6 步骤成功只看元素 → 「元素对、动作错」那条红
- D7 网络错算成答错 → 网络错那条红
- D8 汇总时网络错也进分母 → pass^k 那条红
- D9 被拒的回答不再数它指向了什么 → 被拒那条红
- D10 不核对标注本身 → 标注不合法那条红
