# 02 — 没人在跑的那次调用，要有人把它捡起来

**What to build:**

用户在真机上仍然遇到侧栏停在「正在想」。01 票把**界面状态**的那一类修干净了（界面不再自己记标志位），但**工作本身**还能丢：一次已经派出的模型调用，如果没有任何侧栏在跑它，可以永远挂着，而侧栏如实显示「正在想」——它没说谎，宿主那边确实还有一次调用在途。

> **2026-09-20 由用户报告**（「在其他网页去跑真机时 发现到还是卡在正在想」）。先复现，再修。

**Blocked by:** 01

**Status:** done — 2026-09-21

## 是什么

三件事叠起来，构成一条**永远不会自己好**的路径：

1. **认领这次调用的侧栏消失了**——用户关掉侧栏、换窗口时那个文档被销毁、或者广播压根没送到任何一个侧栏。结果永远回不来。
2. **清扫只在「收到消息」时做**（E-4 的被动检查：结果回来、侧栏挂载、读数到达）。这是 06c 的刻意设计，不加计时器。
3. **读数要求屏上已经有一步**——渲染器只报告屏上那一次呈现的事。而第一次调用还没回来时屏上什么都没有，所以页面放着不动就**再也不会有任何消息**。

并且 `judgeRecovery` 对**没人认领**的调用永远返回「还在进行」（06c：「没人在跑的调用不算迟到」），所以连过期都判不出来。

**复现**（草稿区脚本，桩模型永不回答）：

```
这次调用被认领了：true
认领它的那个侧栏关掉了；另一个侧栏开着，页面上没有任何一步。
  10s：pending=thinking   调用未过期
  65s：pending=thinking   调用未过期
 125s：pending=thinking   调用已过期但还挂着
 170s：pending=thinking   调用已过期但还挂着     ← 不会自己好
```

## 修法

**侧栏的一次拉取，本身就是「这里有一个活着的侧栏」这个事实。** 宿主在答复 `GET_CONVERSATION` 之前先做两件它本来就会做的事：清扫过期的调用，以及把没人在跑的调用重新派出去。两个操作都是幂等的、早就写好的。

这条不违反任何既有规矩：侧栏没有碰 worker 的流程状态（N-6），宿主也没有新增任何猜页面状态的计时——它只是把「被动检查」这件事，接到了一条本来就会到达的消息上。

**并且侧栏在有事情进行时会持续刷新自己显示的东西**（两秒一次，进入就绪即停）。这不是在猜页面，而是刷新它正在展示的那份状态；它同时解决了「提醒丢了就冻住」和「用户就那么看着、没有任何东西触发拉取」。`pull()` 也不再因为一次消息失败而让界面停在旧状态上。
