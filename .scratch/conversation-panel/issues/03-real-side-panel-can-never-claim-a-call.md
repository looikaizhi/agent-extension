# 03 — 真侧栏认领不了任何一次调用

**What to build:**

用户在**真侧栏**里永远停在「正在想」。02 票修的是「没人在跑的调用要有人捡起来」，但真侧栏根本不是「没捡」——它**捡不了**：宿主用 `sender.documentId` 认panel，而真侧栏发来的消息**没有这个字段**。

> **2026-09-21 复现。** 之前六轮真跑、全部 e2e 都是把 `sidepanel.html` 开成**标签页**跑的——标签页有 documentId，所以一路都是绿的。这就是「我和用户操作的差异」。

**Blocked by:** 02

**Status:** done — 2026-09-21

---

## 证据

同一次运行，宿主 `onMessage` 里看到的 sender：

| 侧栏开在哪 | `documentId` | `frameId` | `sender.tab` |
| --- | --- | --- | --- |
| 标签页（我的真跑 / 所有 e2e） | `2C4BB3…` | 0 | 有 |
| **真侧栏**（用户的用法） | **null** | null | 无 |

宿主的认领处理是 `sender.documentId ? claimGuideEffect(…) : false`——真侧栏**每一次认领都被拒**，于是一次模型调用也跑不起来。侧栏没说谎：宿主那边确实挂着一次没人跑的调用。

第二件事是放大器。02 票让一次拉取会去重新派出没人跑的调用，而 `dispatchEffect` 每次都 `pingTab`，侧栏收到通知就再拉取一次：

```
GET_CONVERSATION → handBackUnrun → dispatchEffect → pingTab → 侧栏拉取 → …
```

实测 40 秒里宿主收到 `GET_CONVERSATION` 18531 次、`EFFECT_CLAIM` 18482 次——每秒 320 圈空转，真正那次调用反而一直排不上。

## 修法

**认领者由 panel 自己报名，活没活着由端口说了算。**

1. panel 挂载时给自己起一个名字（`crypto.randomUUID()`），随 `EFFECT_CLAIM` 一起报上去；宿主不再看 `sender`。
2. panel 同时开一条长连接端口。**端口断开就是「这个 panel 没了」**——这是浏览器给的事实，不是靠计时猜的（06c 的规矩仍然成立）。宿主据此判断认领者还在不在。
3. **重新派出不再 ping**：交还一次没人跑的调用并没有改变记录本身，而 ping 会原路变成下一次拉取。回路就此断开。

`documentId` 这条路整条删掉，不留兼容。

## 验收

- [x] 真侧栏（`chrome.sidePanel.open`，非标签页）里问一句能跑到底
- [x] 宿主不再用 `sender.documentId` 认 panel（架构护栏）
- [x] 认领者关掉之后，调用仍能被另一个 panel 接走（端口断开 → 交还）
- [x] 拉取不再自激：一次拉取不会引出下一次拉取
- [x] 类型检查 0，单测、e2e 全绿

## 进度记录（2026-09-21）

- **找到差异的办法**：在 worker 里另挂一个 `onMessage` 计数器，按「发消息的文档 + 时间段」分桶。总数看不出问题，分桶一看就明白：40 秒 18531 次拉取，全部来自同一个文档，而真侧栏那个文档一条都没发出去过——它不是睡着了，是被拒在门外。
- **改动**：`EFFECT_CLAIM` 带上 `panelId`（panel 自己起的名字）；panel 挂载时握一条 `panel:<id>` 端口，宿主用 `onConnect`/`onDisconnect` 维护「现在开着哪些 panel」；`documentId` 这条路整条删掉。交还一次没人跑的调用不再 ping。
- **端口重连有刹车**：接上就断的情况隔两秒再试——没有刹车的重连循环，就是这张票要修的那种空转。
- **e2e 改了一条**：原来那条用 `getContexts({documentIds})` 验「新认领者还活着」，现在认领者是 panel 报的名字，查不到了。改成验真正的那条性质：把新认领者也关掉，宿主应当立刻不再把它当认领者，于是调用又一次被交还——这才是端口在起作用。
- 验证：类型检查 0；单测 993；e2e 263/263；**真侧栏真模型连跑三次**，3 秒内答完，宿主收到的消息从 18531 条降到 7 条。
