# 规格 A：Agent 目录架构

**Status:** ready-for-agent

> 来源：`.scratch/agent-architecture/decisions.md`（拷问五十三问的合并结论，2026-09-12 用户确认）。词汇以 `CONTEXT.md` 为准。本规格是三份中的第一份；规格 B（评估）依赖它，规格 C（workflows 与 memory）依赖 B。

## Problem Statement

**对读这个仓库的人（也是它的主人）：读不懂整个 agent 由什么组成。**

- 一个模型能调用的函数，定义散在六到九个文件里：schema 在一处，识别在一处，校验在一处，提示词里的那段说明在一处，归约器里的后果在一处，trace 摘要在一处，界面效果又在一处。想加一个新能力，要同时改七个地方。
- 目录按运行进程和技术分层切（guide、host、plan、ground），不按 agent 的概念切。读目录名说不出「这个 agent 由哪几块组成」。
- 产品其实有两个 agent：引导和问答。引导有一个整理好的定义；问答的模型逻辑（拼消息、调模型、读回答、修复、核对）却埋在九百多行、零单测的侧栏界面代码里。
- 同一组取值声明了两遍、彼此不引用的有四组：动作枚举、完成依据、上一步结果、intent 名字。「同一个地方」（Place）的判断写了两份，一个失败类型又重新声明了一遍。
- Run record 的 `completed` 名不副实：它只说明每一步用户都点了、页面都变了。第七轮真机里 16 趟 `completed`，按 URL 只有 8 趟真的到了。
- 一个自己在头注释里写着「没接线」的模块还留在树里。
- 站点知识叫 Pack，却和 Descriptor 的绑定、生成代码住在同一个目录里。
- 想加 memory、skills、workflows，不知道往哪里放，也没办法单独开关、单独量效果。

## Solution

按 agent 的概念重排 `src/agent/`：

- **两个 Agent**（引导、问答），各有一个同形状的门面和自己的运行循环。
- **每个 Tool、每种 Output 一个模块**，装齐和它有关的六样东西。`tools/` 只放 Tool：结果会送回模型的函数，今天是 need_docs。回答放在各自 agent 的 `output/` 里。
- **共用的形状与解析**放 `envelope/`；**给模型的说明**放 `prompts/`；**进 prompt 的上下文**放 `context/`；**Thread 的一生**放 `thread/`；**模型端点**放 `provider/`。
- **站点知识改名为 Skill**，成为第一个可以单独开关的 **Plugin**，住在 `skills/`。

**承诺：两个 agent 发给模型的东西逐字节不变。** 由一份在动第一个文件之前冻结的快照来证明。

## User Stories

1. 作为读这个仓库的人，我希望打开 `src/agent/` 就能从目录名说出这个 agent 由哪几块组成，这样我不必先读代码才知道去哪里找。
2. 作为读这个仓库的人，我希望 `src/agent/` 下每个目录名在词汇表里都有词条，这样目录名和我们说话用的词是同一套。
3. 作为读这个仓库的人，我希望知道这个产品有两个 Agent、各自做什么，这样我不会把问答和引导混成一件事。
4. 作为读这个仓库的人，我希望引导 agent 的定义（说明、回答的形状、怎么读、怎么核对、运行循环）集中在一处，这样读一个目录就懂引导怎么和模型打交道。
5. 作为读这个仓库的人，我希望问答 agent 有和引导同形状的定义，不再埋在侧栏的界面代码里，这样两个 agent 可以对照着读。
6. 作为读这个仓库的人，我希望打开 need_docs 的模块就能看到它的 schema、识别、它自己的校验、提示词里它那段说明、它的后果和 trace 摘要，这样一个 Tool 就是一个文件。
7. 作为读这个仓库的人，我希望 guide、clarify、done 各自一个模块，放在引导 agent 的 `output/` 里，这样「回答」和「工具」不混在一起。
8. 作为读这个仓库的人，我希望问答的 explain、clarify、need_text 各自一个模块，放在问答 agent 的 `output/` 里。
9. 作为读这个仓库的人，我希望 `tools/` 里只有「结果会送回模型」的函数，这样看到 `tools/` 就知道模型在回答之前能用什么。
10. 作为读这个仓库的人，我希望 clarify 的形状只定义一次，两个 agent 各自决定拿它做什么，这样同一个形状不必维护两份。
11. 作为读这个仓库的人，我希望 Envelope 的类型、宽容的 JSON 提取、Provenance 扫描器和通用校验住在一个两边共用的地方，这样任何一个 agent 都不必跨进另一个 agent 的目录去拿。
12. 作为读这个仓库的人，我希望给模型的说明分三层放：挑控件、读表、用什么语言回答这类整体的说明放 `prompts/`；每个 Tool、每种 Output 自己的门槛跟着它的模块；user 消息怎么拼放 `context/`。这样改哪一类文字，就去哪一处。
13. 作为读这个仓库的人，我希望归约器只剩分派和 Thread 级的规矩，Fixed plan 有自己的模块，工具后果要用的帮手有自己的模块，这样九百多行的文件不再同时装六件事。
14. 作为读这个仓库的人，我希望 Place、失败类型、四组取值都只有一个所有者，这样改一个取值不必记得去改另一处。
15. 作为读这个仓库的人，我希望 Run record 分开记「这一趟怎么结束的」和「确认了几步」，这样我不会把「都确认了」读成「到了」，也不会把「撞上配额」读成「一步都没确认」。
16. 作为读这个仓库的人，我希望词汇表里有 Arrival 这个词，并写明它和确认程度不是一回事，这样讨论到达率时大家说的是同一件事。
17. 作为读这个仓库的人，我希望没接线的模块被删掉、它记录的教训挪到放等待窗口的地方，这样树里不存在「有测试、没人用」的代码。
18. 作为读这个仓库的人，我希望 Descriptor 的绑定与生成住在以它命名的目录里，这样目录名不再说谎。
19. 作为读这个仓库的人，我希望站点知识改叫 Skill、住在 `skills/`，这样词汇表里的 Skill 从第一天起就对应真实存在的东西。
20. 作为想给 agent 加能力的人，我希望加一个 Tool 只需要在 `tools/` 里建一个模块、再登记一处，这样加能力不用改别处。
21. 作为想给 agent 加能力的人，我希望加一种 Output 只需要在对应 agent 的 `output/` 里建一个模块、再登记一处。
22. 作为想给 agent 加能力的人，我希望新能力可以做成一个 Plugin：放在自己的目录里、登记一处，就能从固定的接缝接进主流程。
23. 作为想给 agent 加能力的人，我希望每个 Plugin 都能单独开关，这样我能量出「带它 / 不带它」的差别。
24. 作为用这个扩展的人，我希望这次重构之后引导和问答的行为完全不变，这样我不必重新适应。
25. 作为用这个扩展的人，我希望站点技能默认照旧生效，这样 github 上的引导不会因为重构变差。
26. 作为维护这个仓库的人，我希望动第一个文件之前先冻结「两个 agent 发给模型的东西」的逐字节快照，并且每一步都和它比，这样「模型看到的东西没变」有证据，而不是一句承诺。
27. 作为维护这个仓库的人，我希望「归约器是纯的」这条守卫守的是归约器能 import 到的所有文件，而不是一个文件名，这样把逻辑搬出归约器不会让守卫静悄悄地失效。
28. 作为维护这个仓库的人，我希望单写者守卫在搬家之后仍然只认一个调用者，这样 Thread 仍然只有一个写入口。
29. 作为维护这个仓库的人，我希望守卫里写死的路径随搬家一起更新，并且在路径失效时变红，这样守卫不会指向不存在的文件。
30. 作为维护这个仓库的人，我希望注释里点名的源码文件在搬家后仍然找得到，这样注释里的知识指得到地方。
31. 作为维护这个仓库的人，我希望逻辑拆分和纯搬家分在不同的票里，这样一旦变红，我分得清是拆错了还是搬错了。
32. 作为维护这个仓库的人，我希望全部做完之后跑一轮真机冒烟，这样产品在真实网站上确实还能启动，而不是只在 fixture 上绿。
33. 作为维护这个仓库的人，我希望问答 agent 能在 node 里直接调用，这样规格 B 的评估能直接调用它，不必开浏览器。
34. 作为维护这个仓库的人，我希望每一趟的 Run record 记下这一趟开了哪些 Plugin，这样之后的评估能把结果归到对应的开关组合上。
35. 作为之后做评估的人，我希望 Plugin 的开关存在设置里、能被 harness 写入，这样一次评估跑之前就能指定开哪些。

## Implementation Decisions

**验收尺**
- **硬指标**：
  - 加一个 Tool = `tools/` 里一个模块 + 一处登记；
  - 加一种 Output = 对应 agent 的 `output/` 里一个模块 + 一处登记；
  - 加一个 Plugin = 它自己的目录 + 一处登记；
  - 只有带来新的界面效果时，才碰各进程的适配层。
- **可读性**：`src/agent/` 下每个目录名，在 CONTEXT.md 里都有词条。

**目标结构**
- `agents/guide/`：引导 agent 的门面、运行循环、trace。`agents/guide/output/`：guide、clarify、done。
- `agents/question/`：问答 agent 的门面、运行循环。`agents/question/output/`：explain、clarify、need_text。
- `tools/`：need_docs，连同「这个链接能不能抓」的判定。
- `envelope/`：Envelope 类型、宽容的 JSON 提取、Provenance 扫描器、通用校验（ref 在表内、敏感控件）、clarify 的共用形状。
- `prompts/`：每个 agent 的系统提示词各段、修复轮提示词。
- `context/`：元素表序列化 + nonce 包裹、历史文本、新出现的 ref；负责收集 Plugin 的贡献。
- `skills/`：站点技能（由 Pack 迁来）。
- `thread/`：归约器（分派与 Thread 级规矩）、Fixed plan 模块、帮手模块（画一步、记账、通知、发模型调用）、单写者、Effect、重新规划、Run record。
- `provider/`：用户自带的模型端点。
- 仓库其它地方：Descriptor 的绑定与生成移到 `core/` 下以 descriptor 命名的目录；`core/security/` 不动；不新建 `copy/`，也不新建 `authorization/`。

**一个 Tool / Output 模块装六样**
1. schema：给模型的函数定义或回答形状；
2. 识别；
3. 它自己的校验规则；
4. 提示词里它那段门槛说明；
5. 后果；
6. trace 摘要。

- 界面效果留在各进程的适配层：`agent/` 下禁止 `chrome.*`，这条守卫不变。
- 后果是纯函数，由归约器分派调用，受纯度守卫约束。

**两个 Agent 的门面同形状**
- 都有：名字、说明、拼消息、回答形状、读回答、核对。
- 各有自己的运行循环：修复轮的形状本来就不同，引导重发整份请求再附一对说明，问答是一段不含页面的全新对话。
- 问答继续用自由文本 JSON，不改用 tool calling。两者共用 Provider。

**clarify 是一个 Intent**：形状、识别、Provenance 只有一份；引导里拿它让 Thread 停下来等用户，问答里拿它列出候选并全部框出。

**Plugin 机制（本规格只引入 Skill 用得到的那一处）**
- 每个 Plugin 有一个名字，默认开或关。
- 本规格只引入「往 Context 加一段文字」这一个接缝。「引导开始时给建议」和「一趟结束时拿到记录」两个接缝，由规格 C 随第一个用到它们的 Plugin 引入。
- Plugin 的贡献在归约器之外收集（读存储是异步的），随调用参数交给 agent。归约器不知道有哪些 Plugin。
- 开关存在设置里（与 trace 开关同一类存储），harness 能在跑之前写入。每一趟的 Run record 记下开了哪些 Plugin。
- **Skill 是第一个 Plugin，默认开**：按域名加载，文字与位置和今天的站点知识完全相同，快照逐字节不变。「站点知识」这个词退场。

**归约器**
- Output 与 Tool 的后果搬出之后，归约器只剩：分派、结果闸门（过期结果丢弃、世界已变就作废、配额）、开始、页面变了、绑定结果、等待超时、跨站确认（处理用户的回答；要不要先问，由 guide 的后果决定）。
- Fixed plan（开始、前进、用过 / 跳过）自成一个模块，保持「永不调用模型」。
- 纯度守卫的范围改成「归约器在运行时能加载到的所有源码文件」，按依赖闭包算。不止 `src/agent`：归约器间接加载的 `core/` 文件同样必须是纯的。单写者守卫仍然只认一个调用者。

**去重**
- 四组取值（动作枚举、完成依据、上一步结果、intent 名字）各只有一个所有者；给模型的 schema 从同一份取值生成。
- Place 只剩一份实现。
- 失败类型不再重新声明。
- 线上协议那三个有意复制的类型（为防循环依赖，理由写在代码里）不动。

**Run record 与 Arrival**
- 今天的单一状态值混着两件事：`abandoned` 既表示「一步都没确认」，也表示「被配额或跨站凭据强行停下」（后者即使前几步已确认也写它）；打转兜底又直接写成「部分完成」。
- 改成两个字段：**怎么结束的**（模型说到了、步骤走完了、打转兜底、配额用完、跨站凭据停止、用户结束、关浮层、关标签页、被新的一趟接替）与**确认了几步**（全部、部分、一步都没有，只按历史机械计算）。旧的单一状态值删除，不留兼容；读它的地方一并改。
- 本规格不引入任何「到了吗」的产品行为，只让记录不再误导。

**删除没接线的模块**：它记录的教训（多数重新规划等不到页面稳定、会把整个窗口烧完）挪进放等待窗口的那段注释。

**顺序：先在原目录里把逻辑拆好，最后一张票只改路径**
1. 冻结快照；
2. 去重；
3. Run record 改名；
4. 删没接线的模块；
5. 问答 agent 搬出侧栏；
6. 拆 Output / Tool / 帮手 / Fixed plan 模块，纯度守卫改成依赖闭包，引入 Plugin 机制与 Skill；
7. 纯搬家：目标结构、Descriptor 目录、prompt 三层拆分，守卫路径与注释引用同步更新；
8. 真机冒烟。

2、3、4 互不依赖，可以并行。

## Testing Decisions

**好的测试只断言外部行为。** 这次的外部行为就是：两个 agent 发给模型的东西、归约器对输入给出的状态与效果、宿主对存储做了什么、页面上出现了什么。

**唯一的新切面：「发给模型的东西」快照。**
- 切在两个 agent 的门面上：给定目标、元素表、历史、Skill 贡献、新出现的 ref，产出 system 消息、工具 schema（或回答形状说明）与 user 消息。
- 用现有 golden 语料里的输入，在动第一个文件之前冻结。之后每张票逐字节比对。
- Plugin 全关时，快照同样要有一份，证明「不开 Skill」只是少了那一段，别处一个字不变。

**沿用的切面**

| 断言什么 | 切面 | 现有的先例 |
|---|---|---|
| Output、Tool 的后果和 Fixed plan 搬家后行为不变 | 归约器 `step()`，纯对象进纯对象出 | 归约器测试文件，上百条用例 |
| Run record 改名、Plugin 组合被记下 | 宿主那层的注入式测试 | 引导与步骤测试文件，已经在记录存储调用的顺序 |
| 问答 agent 的运行循环（修复一次、不成环、失败分类） | 门面加一个假的 `complete` | 引导运行循环的测试文件 |
| 纯度守卫按依赖闭包、单写者、路径与注释引用 | AST 架构守卫 | 架构守卫测试文件，每条都带「范围非空 + 判据在树上命中」的自检 |
| 接线 | e2e 冒烟，问答 QA-1 到 QA-11 原样保留 | 现有 183 条 |
| 抽取不受影响 | 抽取器评测 | 现有门槛 |

每张票的验收：类型检查、单测、e2e、抽取器评测全绿，并且快照逐字节一致。最后一张票之后跑一轮真机，只作冒烟，不作版本比较。

## Out of Scope

- 规格 B 的评估，以及规格 C 的 Workflow、Memory、「到了吗」。
- 问答 agent 改用 tool calling。
- 由模型挑选、按需读 Skill 的全文（触发条件记在 decisions.md）。
- 线上协议里那三个有意复制的类型。
- 导航重新规划「抓住加载完成后的后续渲染」：影响的是规划质量，需要重新设计重新规划队列怎么让位。
- 引导结束通知缺少标签页标识：已知缺陷，另开。
- `GuideContext` 与 `CallModelParams` 的字段重复：注释写明是有意的。

## Further Notes

- **这是一次宽重构，import 的波及面覆盖全仓**：计划、宿主、引导、Provider 四处合计被六十多个文件引用，Descriptor 目录被九个。所以采用「先拆后搬」：拆的票只改逻辑，搬的票只改路径。
- 架构守卫和「注释里点名的源码文件都还在」那条守卫都按路径写死。搬家时它们会先变红，逼着引用一起更新，这正是我们要的。
- 词汇表这次已经新增或修改的词条：Agent、Tool、Output、Context、Provider、Plugin、Skill、Workflow、Memory、Arrival、Decision eval、Task eval、Thread、Intent、Question、Run record。实现时如果发现代码和词条对不上，以词条为准，并回来修词条的措辞。
