# Agent 目录架构、评估与三项能力：拷问结论（2026-09-12，合并版）

- 拷问材料：`.scratch/agent-architecture/grill-brief.md`
- 研究：`docs/research-agent-skills-workflows-memory.md`、`docs/research-agent-evaluation-metrics.md`
- 词汇表 `CONTEXT.md` 本次的改动：
  - 新增：Agent、Tool、Output、Context、Provider、Skill、Workflow、Memory、Arrival、Decision eval、Task eval
  - 修改：Thread、Intent、Question、Run record

## 一、验收尺（Q1）

- **硬指标**：
  - 加一个 Tool = `tools/` 里一个模块 + 一处登记；
  - 加一种 Output = 对应 agent 的 `output/` 里一个模块 + 一处登记；
  - 只有带来新的界面效果时，才碰各进程的适配层。

  今天的基线是 6–9 个文件。
- **可读性**：`src/agent/` 下每个目录名，在 CONTEXT.md 里都有词条。
- **有效性**（Q42）：一个目录只有在它的功能通过 eval 之后才落地。

## 二、目标目录树（Q17 → Q36、Q37、Q38、Q40）

```
src/agent/
  agents/
    guide/          引导 agent：门面、运行循环、trace
      output/       guide、clarify、done（Output，经 tool calling 交回）
    question/       问答 agent：门面、运行循环（从 App.tsx 搬出）
      output/       explain、clarify、need_text（Output，经 JSON 文本交回）
  tools/            need_docs（Tool；带「这个链接能不能抓」的判定）
  envelope/         Envelope 类型、宽容 JSON 提取、Provenance 扫描器、通用校验、clarify 的共用形状
  prompts/          每个 agent 的系统提示词、修复轮提示词
  context/          元素表序列化 + nonce 包裹、历史文本、新出现的 ref；负责把 skills（将来还有 memory）读进来
  skills/           站点技能：由 Pack 迁来，按域名加载
  thread/           归约器、Fixed plan、帮手模块、单写者、Effect、重新规划、Run record
  provider/         用户自带的模型端点
  workflows/        规格 C，通过 eval 才落地
  memory/           规格 C，通过 eval 才落地
core/descriptor/    bind.ts、author.ts（从 core/packs 移出）
evals/              extract/、decision/、task/
tests/              unit/、e2e/（不变）
```

- 每个 Tool、每种 Output 自己的那段说明（「什么时候才该用我」），跟着它自己的模块放。
- 每个模块装六样（Q8）：schema、识别、它自己的校验规则、那段说明、后果、trace 摘要。
- 界面效果留在各进程的适配层。
- 不单列 `copy/`（Q33），也不新建 `authorization/`（Q34）。`core/security/` 保持原样；跨站判定留在 `thread/`——指归约器处理用户对跨站卡片的回答。「这一步要离开本站，先问一句」是 guide 回答的后果，随 guide 模块走（第 10 张）。

## 三、规格 A：Agent 目录架构

承诺：**两个 agent 发给模型的东西逐字节不变。**

1. **冻结逐字节快照**（Q21）：对 golden 语料的固定输入，存下两个 agent 实际发出的 system 消息、工具 schema 和 user 消息。
2. **去重**（Q5、Q35）：
   - 四组取值：
     - 动作枚举：`agent.ts:183` ⇄ `validate.ts:39`
     - 完成依据：`agent.ts:244` ⇄ `contract.ts:65`
     - 上一步结果：`agent.ts:136` ⇄ `contract.ts:118`
     - intent 名字：`validate.ts:69` ⇄ `contract.ts:227`
   - 另加两处纯重复：Place（`machine.ts:356` ⇄ `background.ts:246`）、EffectFailureKind（`machine.ts:60`）。
   - protocol.ts 那三个线上类型不动。
3. **Run record 改名 + Arrival**（Q16）：状态名改成确认程度（全部 / 部分 / 一步都没有），具体名字到实现时再定。
4. **删 `settle.ts`**（Q20）：它记录的教训挪进 `replan.ts` 放等待窗口的那段注释。
5. **问答 agent 搬出 `App.tsx`**（Q10）：门面和引导同形状，有自己的运行循环，继续用自由文本 JSON。
6. **拆模块**（Q8、Q19）：引导的 Output 与 Tool 模块、帮手模块、Fixed plan 模块；纯度守卫的范围改成「归约器在运行时能加载到的所有源码文件」，按依赖闭包算。
7. **纯搬家**：目标目录树；`core/packs` 拆开，Pack 迁进 `skills/`，这个词随之退场（Q18、Q40）；prompt 按「策略 / 拼装 / 各自的说明」拆开。
8. **一轮真机冒烟**（Q21）。

- 2、3、4 互不依赖，可以并行。
- 每张票都要求：类型检查、单测、e2e、抽取器评测全绿，并且快照逐字节一致。
- 顺序是先在原目录里把逻辑拆好，最后一张票只改路径（Q26）。

## 四、规格 B：Agent 评估

依赖规格 A 的第 5、6 步（Q27）：eval 要能在 node 里直接调用两个 agent。

- **两层**（Q15）：Decision eval（离线，当闸门）与 Task eval（真机，量能力）。
- **位置**（Q38）：
  - 仓库根目录 `evals/`，下面是 `extract/`（今天的抽取器评测，原样搬进来）、`decision/`、`task/`（harness 与 score-run 从 `tests/spike/` 搬过来）。
  - 命令是 `npm run eval`（抽取器，不变）、`eval:decision`、`eval:task`。`tests/spike/` 只留一次性探针。
- **Decision eval**：
  - 打分（Q29）：意图对不对 + 第一步的元素与动作在不在可接受集合里；后续步骤只查「在表里、不是敏感控件」。
  - 标准答案（Q23）：人标的可接受集合，从到达了的轮次预填，你确认或补充。第一批标 50–80 个状态。
  - 语料（Q24）：harness 每跳之后把 trace 读走写进 ndjson；产品那 24 条的上限不动。
  - 覆盖范围（Q32）：先只覆盖引导 agent。
- **Task eval**：
  - 由谁判（Q25、Q30）：你的判定是正式分数，在报告页上做、存进报告页的数据库，再拉成仓库里的 JSON。每个目标另写一份程序化判据（可接受的最终 URL + 可接受的最后一步），报告它和你的判定的一致率、precision、recall。
  - 任务集（Q22）：github.com 约 10 个、gitee.com 约 8 个、help.aliyun.com 约 8 个目标，每个跑 3 遍。目标清单我起草，你定稿。
- **门槛与报告**（Q31）：
  - Decision eval（设门槛）：
    - 解析失败率、校验失败率不高于冻结基线；
    - 指向表外或敏感控件 = 0；
    - 意图准确率与第一步准确率：配对比较不显著变差。
  - Task eval（只报告）：
    - 按目标聚类的 Arrival 率，附 Wilson 置信区间；
    - pass^1–3；
    - 和上一轮的配对差；
    - 跳数、调用数、token、成本；
    - 安全违规数；
    - 程序化判据的一致率。
  - 两层都手动跑，不进 `verify`。改提示词、换模型、加 memory 或 skill 之前，必须跑 Decision eval。

## 五、规格 C：workflows 与 memory 的第一版（Q42、Q52）

依赖规格 B。每一样都是一次实验：通过 eval 才合进来，目录才出现。

- **共用的地基**：
  - 引导结束时，只要侧栏开着就问「到了 / 没到」，关标签页那种结束除外；不答就不存（Q41、Q51）。
  - Run record 每一步补记：Descriptor、动作、建议输入的值、在哪一页提出、落到了哪一页（Q43）。
- **Workflows**（先做）：
  - 生成：你答「到了」时，从那条 Run record 生成。
  - 匹配（Q44）：你开始引导时，侧栏列出同站点、目标最接近的至多 3 条，你点了才回放。「最接近」用现成的中英文分词算词重叠，只用来排序。
  - 回放（Q45）：新增计划来源「workflow」，平时像 Fixed plan 一样不调模型；某一步找不到目标时，交给模型接着规划。检视器的 Fixed plan 不变。
  - 量（Q46）：Task eval。第 1 遍到了就存 workflow，第 2、3 遍回放；「到了吗」由程序化判据代答。算有效的条件：Arrival 不显著变差，回放那几遍的模型调用接近 0。
- **Memory**（后做）：
  - 存什么（Q47）：原样存你确认到了的那一趟路（目标、站点、每一步的标题与落到的页面、终点），不经模型加工。
  - 怎么取（Q48）：只取同站点、目标最接近的 1 条，过门槛才用；正在回放 workflow 时不取。放在 user 消息里，站点技能之后、不可信页面内容之前，写明「仅供参考」，并限制长度。
  - 存多久（Q49）：`storage.local`，每站最新 20 条。侧栏「记忆」区能看、能删、能清空。
  - 量（Q50）：Decision eval 当闸门，带 / 不带 memory 做配对比较，memory 必须来自别的目标（留出法）；Task eval 只确认不退步。

## 八、Plugin（2026-09-12，写规格时用户追加）

- memory、skill、workflow 以及以后的新能力，都做成可以单独开关的 **Plugin**。harness 的 main 函数和 Decision eval 能按次选开哪些。
- **只从固定接缝接入，接缝随第一个用户出现**：
  - 往 Context 加一段：规格 A 随 Skill 引入。
  - 引导开始时给建议：规格 C 随 Workflow 引入。
  - 一趟结束时拿到记录：规格 C 随 Workflow 与 Memory 引入。
- Plugin 的贡献在归约器之外收集，因为读存储是异步的，然后随调用参数交给 agent。归约器不知道有哪些 Plugin。
- 开关存在设置里；每一趟的 Run record 记下开了哪些。
- 默认值：Skill 开（逐字节不变）；Workflow 和 Memory 关，通过 eval 后才默认开。
- 加一个 Plugin = 它自己的目录 + 一处登记。

## 实现中定下的例外

- **校验先后（第 10 张）**：
  - **现在的先后**：一份计划同时违反两个 agent 共用的规矩（ref 不在表内或敏感，R-a/R-e）和 guide 自己的规矩（R-b、R-d、R-f）时，报共用的那条。第 10 张之前，R-d 排在 R-a/R-e 之前。
  - **为什么**：共用的规矩在门面里先跑，各模块自己的后跑。原先 R-a/R-e 夹在 R-d 与 R-f 之间，只用一个钩子无法保留原先后。
  - **影响**：只影响同时犯两种错的计划，报出的仍是真实的错。但这句话会进修复请求和 trace，修复也失败时还会显示给用户，所以这是用户故事 24「行为完全不变」的一处有意例外。
  - **不变的**：R-f 仍在 R-e 之后。只点一个敏感输入框的计划报的是「敏感」，不会被说成「再给它一步 input」。
  - 两件事都有测试钉住。
- **need_docs 的循环先不补通**：宿主判定能抓之后，还不会把请求交给侧栏，文档正文也回不到模型；目前会如实告诉用户做不到。整个架构升级（规格 A）做完之后，再针对它单独开票，不排进 A 的票里。
- **问答快照改了一行（第 05 张，按推荐批准）**：
  - **起因**：问答快照改由运行循环驱动之后，修复请求只会在首次回答读不出时发出。原快照里那段「坏回答」只少一个右花括号，解析器的截断修复能把它救回来，产品遇到它根本不会发修复请求，所以原快照记的是一次不会发生的请求。
  - **做法**：换成在字符串中间截断、真正救不回来的写法。快照因此只有修复请求里引用的那一行变了；产品自己写给模型的文字仍逐字节不变。
  - **为什么不保留原文件**：不改文件的唯一办法是直接调用修复消息的构造函数，那样就证明不了「修复引用的是首次回答的原文」。
- **两个 agent 互相加载对方的登记处（第 11 张，按推荐批准）**：
  - **做法**：全部 intent 的清单由两个登记处推出，两个 agent 读回答时都用它，才分得清「别的 agent 的回答」（如实说，不修复）和「坏形状」（修复一次）。代价是问答 agent 在运行时会加载引导的登记处，并连带加载引导的模块，反过来也一样。
  - **与用户故事 11 的冲突**：故事 11 说「任何一个 agent 都不必跨进另一个 agent 的目录去拿」。两个 agent 自己的代码都不 import 对方的门面或运行循环，但清单文件把对方的登记处带进来了。
  - **为什么不另写**：唯一的替代是各 agent 手写一份 intent 名单再用编译期断言核对，那正是第 11 张要去掉的手写清单。
  - **守着的边界**：共享层（契约、校验、提示词）不得加载任何一个登记处或这份清单，有架构守卫。
- **引导调用收到问答的信封，直说收到了什么（第 11 张，按推荐批准）**：
  - **做法**：模型调了 explain 这个不存在的工具，或文字回答里写了 explain / need_text 时，引导运行循环不修复、不核对，归约器照原样显示「模型返回了非引导类信封（intent: X）」。
  - **与以前的差别**：以前会先认出问答的形状，再跑 R-a/R-e，形状残缺或 ref 不对就修复一次。所以这两种情况下，实际调用次数、配额扣减和 trace 条目都与以前不同。
  - **为什么接受**：把问答的回答硬修成引导计划本身就不对；要恢复旧行为，引导就得认得问答的信封形状，等于跨进对方目录。这种情况只在模型调了不存在的工具，或在文字回答里写问答信封时出现，很少见。
- **Plugin 开关按趟生效（第 12 张评审后续，用户批准「修」）**：
  - **做法**：开关在一趟开始时读一次，存在线程旁边，这一趟的每次模型调用都用这一组，结束时原样记进 Run record，线程删除时一起删。
  - **与票面原文的差别**：票里原写「设置里改了开关，下一次模型调用就生效」。现在一趟中途改开关，要到下一趟才生效。
  - **为什么**：用户故事 34 要求 Run record 能「归到对应的开关组合上」。一趟若在中途换了组合，调用和记录就对不上，这一趟也归不到任何一个组合。harness 本来就在跑之前写开关，所以这对评估没有代价；产品里也还没有给用户的开关界面。
- **guide 的两段门槛暂留在说明目录（第 13 张评审，用户批准「修」时同意暂不改）**：
  - **现状**：`prompts/system.ts` 的工具选择开头写死了「默认是 guide」，收尾讲的是 guide 回答的 route 与 value 该怎么写。按「每种 Output 自己的门槛跟着它的模块」，这两段应该归 guide 模块。
  - **为什么没在搬家时挪**：它们在系统提示词里夹着各 intent 的门槛行，挪进 guide 模块就要改拼装顺序，快照需要重新核对。第 13 张只改路径。
  - **之后**：另开票处理，届时要核对快照逐字节不变。
