# 08 — need_docs 成为第一个 Tool 模块

**What to build:**

need_docs 是今天唯一的 `Tool`。把属于它的六样东西，外加「这个链接能不能抓」的判定，集中到一个模块里：

1. 给模型的函数定义；
2. 识别；
3. 它自己的校验规则；
4. 提示词里它那段门槛说明；
5. 后果（发起文档抓取）；
6. trace 摘要。

这张票同时定下所有 Tool 与 Output 模块共用的形状，以及「登记一处」的机制：引导 Agent 从登记处拿到工具列表、识别、校验、后果和 trace 摘要。界面效果留在各进程的适配层。

**Blocked by:** 02 — 同一个取值只有一个所有者；06 — 归约器的帮手成为独立模块，纯度守卫改成按依赖闭包算

**实现记录**
- **归约器的输入、输出类型已移到 Thread 的类型文件。** 各个模块从此不必 import 归约器文件。原来有两个同名的 `EffectOutcome`，现合并为线上那一个；「值要转成字符串」这一步从宿主挪进归约器，宿主里那段手工转换已删除。
- **工具 schema 的辅助函数单独成一个文件**，所有 intent 模块写 schema 都用同一套形状。
- **need_docs 模块装齐了六样，外加「这个链接能不能抓」的判定和它自己的文档抓取配额。**
- **登记处是 intent 进入引导 agent 的唯一入口。** 以下各处都先问它：工具列表、系统提示词里那一行、两条识别路径、识别失败时告诉模型的形状提示、校验时它认领的 ref、trace、归约器的后果。
- **快照逐字节不变。**
- **「登记是唯一入口」有测试证明**：把登记处清空后，need_docs 从工具、提示词、两条识别路径里全部消失。另外验证了三种在模块外面另写一份的做法（识别里、工具列表里、提示词里），各自都会让这条测试变红。
- **过程中查实的问题**：need_docs 的循环只接了一半。宿主判定能抓之后，并不会把请求交给侧栏；文档正文也不会回到模型，目前会如实告诉用户做不到。本票承诺行为不变，所以没有补通这条链路；只把宿主里那段说错的注释和词汇表 Tool 词条改成了实话。补通它是新功能，需要单开一张票。

**评审后续（已修）**
- **依赖方向倒过来**：契约、校验、提示词不再加载登记处，改由引导 agent 的门面先问登记处，再回落到两个 agent 共用的识别与校验。原因有二：共享层加载登记处，问答路径为了读一个信封就要把引导的零件一起加载；等第 10 张的 guide 模块从契约按值 import 时，还会形成真正的循环。现在有一条架构守卫守着：共享的这三个模块，依赖闭包里不得出现登记处。
- **系统提示词的拼装挪进门面**：「四个工具对应四种回答」那一段在各模块的那一行处拆开，由门面按登记顺序拼接。快照逐字节不变。
- **登记处只保留一处强转**：按信封查模块的函数改为泛型，调用方拿到的模块类型与信封精确对应。
- **判定函数搬进 need_docs 模块**：「这个链接能不能抓」的判定搬了进来，原来的目录已删除。
- **两道闸门合成一个共用函数**：「有请求在路上就不发、超了配额就停」，模型调用和文档抓取都用它。
- **非字符串的值当成解析错误**：以前在改动前后都会直接抛异常，现在按解析错误处理。
- **过时注释全部改成实话**：包括 Effect 定义和测试里的「pending 06」「没有地址」。
- **名不副实的测试改成真的走 need_docs**：原来那条「need_docs 不得把线程焊死」传的是 guide，现在真的走 need_docs，覆盖了「告诉用户读不了」的分支。
- **测试改走引导 agent**：直接用共享函数测 need_docs 的测试（契约、校验、变异语料、一致性），全部改成通过引导 agent 的门面，因为 need_docs 本来就归它。
