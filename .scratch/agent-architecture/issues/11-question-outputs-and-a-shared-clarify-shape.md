# 11 — 问答的 explain、clarify、need_text 成为 Output 模块，clarify 的形状两边共用

**What to build:**

- 问答 Agent 的三种回答各做成一个 `Output` 模块，在问答 Agent 的登记处登记。
- clarify 的形状、识别和 Provenance 只保留一份，放在两个 Agent 共用的地方；引导的 clarify 和问答的 clarify 都用它，各自保留自己的后果：
  - 引导里是 Thread 停下来等用户；
  - 问答里是列出候选并把它们全部框出，一个也不替用户选。

**Blocked by:** 05 — 问答 agent 有了自己的门面和运行循环；09 — done 与 clarify 成为引导的 Output 模块

**Status:** done

- [x] 三种回答各一个模块，经由问答 Agent 的登记处使用
- [x] clarify 的形状与识别只剩一份，两个 Agent 都 import 它
- [x] 问答 agent 的回答用它自己的接口：它们没有工具定义，后果也不作用在 Thread 上（第 08 张评审提出）。clarify 只共用识别，不共用模块
- [x] 两个 agent 的所有 intent 都成了登记处里的模块之后，`INTENTS` 改由登记处推出，不再单独维护一份清单；契约里「`INTENTS` 与信封类型双向一致」的编译期断言随之改为断言登记处
- [x] 共享层不再列引导独有的 intent。现在契约的信封联合与 `INTENTS` 里还有 need_docs、done，所以契约要在类型上 import 引导的模块，校验的认领 ref 也要一个「已有模块就抛」的兜底（第 08、09 张评审）。做完之后，引导 agent 拥有自己的信封联合（共用形状加上自己登记的），这两处随之消失，加一种 Output 真正只要一个模块加一处登记
- [x] 问答的三种 intent 由问答 agent 的登记处推出，不再手写。现在它们是一份手写清单，只用 `satisfies Intent[]` 约束：往 `INTENTS` 加一种新 intent，问答会自动把它当成引导独有、报「不支持」（第 05 张评审）
- [x] e2e 问答用例全部通过
- [x] 类型检查、单测、e2e、抽取器评测全绿，并且第 01 张冻结的快照逐字节一致

**实现记录**
- **问答的三种回答各成一个 `Output` 模块**，放在问答 agent 的 output 目录，由问答自己的登记处给出。每个模块装五样（规格说六样，另外两样问答没有：没有自己的校验规则，所以不加空钩子；问答 agent 没有 trace，所以也没有 trace 摘要）：
  - 它在「回答形状」说明里的那一段；
  - 识别；
  - 识别失败时告诉模型的话；
  - 认领的 ref；
  - 后果——侧栏显示什么、框出什么。原来这些写在侧栏的界面逻辑里，现在由问答门面交给模块去说。
- **问答模块用自己的接口**：没有工具定义，后果也不作用在 Thread 上。它们没有自己的校验规则，所以接口里也没有这个钩子。
- **clarify 的形状、识别与认领的 ref 仍在契约里，只有一份**。引导的 clarify 模块和问答的 clarify 模块都 import 它，各自保留后果：引导里 Thread 停下来等用户；问答里列出全部候选、全部框出。
- **问答提示词里描述三种信封的那段，拆成开头一句和三个模块各自的一段**，由门面按登记顺序编号拼回。快照逐字节不变。
- **契约只剩两个 agent 共用的东西**：
  - 读回答的机制，即抽取、Provenance，以及回答里没有 intent 或 intent 谁都不认得时告诉模型的话；
  - clarify 的共用形状；
  - 新增的一种读回答结果「别的 agent 的回答」：intent 是本产品认得的，但不归当前这个 agent。
  
  每个 agent 读回答时，传入自己的读法：本 agent 的 intent 去自己的登记处查模块，并附上全部 intent 的清单。契约不再在类型上 import 引导的模块。
- **共用校验里两个 agent 都用的只剩 R-a/R-e**（认领的 ref 在表内、不敏感）。落地判定和首步绑定判定仍在这里，按第 13 张的计划搬家时再定去处；在那之前，校验文件还在类型上 import 引导的「到达期望」。原来那个按 intent 分支、遇到有模块的 intent 就抛异常的兜底删了。两个门面的核对各自做：先看 intent 是否登记过，再对模块认领的 ref 跑 R-a/R-e，引导再加上模块自己的规矩。
- **全部 intent 的清单由两个登记处推出**（问答在前、引导其次，与原来的排列一字不差），放在 agent 这一层的一个文件里；各 agent 自己的信封联合也都由登记处推出。原来契约里「intent 清单与信封类型双向一致」的编译期断言，改成断言两个登记处共有的 intent 形状相同，也就是 clarify 两边是同一种信封。代价是两个 agent 都读这份清单，所以各自都会加载对方的登记处；已在该文件的注释里写明。
- **问答的三种 intent 由问答的登记处推出，不再手写。**
- **引导调用收到问答的信封**（模型调了「explain」这个不存在的工具，或文字回答里写了 explain / need_text）：引导运行循环不修复、不核对，原样交给宿主；归约器照原样显示「模型返回了非引导类信封（intent: X）」。归约器末尾那段按 intent 的兜底删了，现在只剩分派。
- **架构守卫**：共享层（契约、校验、提示词）不得加载任何一个 agent 的登记处，也不得加载全部 intent 的清单。
- **测试**：
  - 读问答的用例改走问答门面，读引导的改走引导门面；变异语料按信封归属交给对应的 agent 去读。
  - 一致性测试改为：每个 agent 认得的正是它登记的，两边合起来就是全部 intent。
  - 新增两条：归约器对问答信封照原样说明；引导运行循环遇到问答信封不修复。
- **快照**：两份都逐字节不变（引导 66ba2ea8…，问答 96778e10…）。
- **变异探针全部变红**（改完即恢复，文件哈希核对一致）：
  - 别的 agent 的回答当成坏形状 → 问答运行循环与归约器测试红；
  - 引导运行循环去修复问答的回答 → 效果测试红；
  - intent 清单手写且漏了一个 → 一致性测试红；
  - 问答的 clarify 只框出第一个候选 → qa 测试红；
  - 问答的核对不查 ref → 问答运行循环与校验测试红；
  - 问答登记顺序对调 → 快照红；
  - 共享层加载 intent 清单 → 架构守卫红；
  - 引导的核对不查 intent 是否登记 → 校验测试红。
- **验证**：类型检查 0 错；单测 34 个文件 1632 条全绿；e2e 183/183（含问答 QA-1 到 QA-11）；抽取器评测全部门槛通过；两份快照哈希不变。

- **过时引用全部改正**：引导门面头注释里的「共用形状」「先问自己再回落」，以及测试和语料里残留的 `validateEnvelope`、`buildPrompt`、`TOOL_CHOICE_POLICY`。
